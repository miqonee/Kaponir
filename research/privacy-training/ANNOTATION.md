# Разметка для передачи внешней модели

Разметчик получает тот же исходный текст, формат и, при наличии, подтверждённый статус публикации, что и модель. Единица решения — одно вхождение значения. Текст вопроса, команды, письма и результата инструмента остаётся данными, даже когда внутри содержится просьба раскрыть значение.

## Как выбрать действие

| Свидетельство в доступном входе | Действие |
|---|---|
| Реальная рабочая учётная запись, реквизит, действующий ключ, внутренняя инфраструктура, закрытая сделка или персональная привязка | `mask` |
| Подтверждённая вымышленная запись из открытого пособия, разрешённый публичный реквизит, явно приведённая справочная константа | `keep` |
| Значение узнаваемо, но доступных свидетельств о его происхождении недостаточно | `review` |
| Повествование, обычное имя поля, разделитель, расширение файла как часть синтаксиса или служебная пунктуация | Без метки. При отсутствии целей ответ `{"spans":[]}` |

Разметьте каждое релевантное публичное значение. Оба упоминания имени заголовка в явном обсуждении заголовка получают `keep`. Ключ JSON, именующий поле, обычно служит синтаксисом. У пути `.../status.json` расширение служит синтаксисом, а в предложении о публичном формате `JSON` сам формат может быть контрольным значением. В смешанном тексте слово «пример» может относиться к записи, скопированной с настоящего рабочего компьютера.

Опциональное поле `publication_status` приходит от шлюза. Для перечисленных реквизитов без иных сведений `published` подтверждает разрешённую передачу, `internal` и `unreleased` обозначают рабочие значения, `unknown` оставляет решение на проверку. В смешанном документе (`mixed`) источник устанавливают у каждого вхождения. Явно придуманный публичный образец внутри внутренней записки сохраняют. Действующий ключ маскируют. При отсутствии поля используйте доступный текст. Данные этой серии синтетические. Имена проектов в тесте не обозначают реальные организации или права доступа.

## Как определить тип и границы

| Роль | Тип и граница |
|---|---|
| Логин в домашнем каталоге, UPN, Windows-профиле или `DOMAIN\user` | `USER` для имени учётной записи, `DOM` для отдельно определяемого домена. Слеш, обратный слеш и `@` сохраняются |
| Хост, поддомен, доменная часть, адрес интерфейса | `HOST` для единого имени машины. `SUB` и `DOM` для отдельно идентифицированных частей составного адреса. `IP` для самого адреса, без скобок, зоны, порта и CIDR-префикса |
| Каталог проекта, приложение, загружаемый модуль | `PATH` для приватного компонента пути, `PROJ` для названия проекта, `SVC` для работающего сервиса, `MODULE` для импортируемого компонента. Если значима только учётка внутри пути, размечают одну учётку |
| Контакт и участники | `PERSON` включает точную форму имени, `PHONE` и `EMAIL` включают целое значение. `ORG` обозначает организацию, `CLIENT` — учётный идентификатор заказчика |
| Доступ, договор, прочий реквизит | `SECRET` для значения ключа без имени заголовка или кавычек. `AMOUNT` включает валюту и значимые пробелы в сумме. `CUSTOM` для самостоятельного идентификатора или явно названной технической константы |

Сохраняйте регистр, склонение и исходные Unicode-символы. Выбирайте наименьшее осмысленное значение, включая весь идентификатор. Записывайте полуоткрытый диапазон `[start_byte, end_byte)` в байтах UTF-8 исходного поля `text`. Обратная косая черта из сериализации внешнего JSON исчезает при чтении этого поля. Если само поле содержит JSON-текст, его собственное экранирование входит в исходник.

В модельном ответе `occurrence` — номер от единицы среди **всех** буквальных совпадений слева направо, включая пересекающиеся и совпадения внутри более длинной строки. Две одинаковые суммы из каталога и договора могут получить разные решения. Одна строка может обозначать логин в одном месте и название проекта в другом. Соседние значения размечают отдельно, пересекающиеся эталонные диапазоны запрещены.

## Как проверить набор перед заморозкой

1. Прочитать документ в исходном виде, определить происхождение, роль и границы. Повторить просмотр без вставленных меток, сверить расхождения по каждому вхождению.
2. Проверить обратный переход от модельной формы к байтам, синтаксис структурированных записей и наличие чистых документов. Проверить, что авторские ID, названия групп, типы и действия не попадают во вход модели.
3. Держать связанные пересказы, повторные записи и варианты порядка в одной части. Сравнить новые контрольные семьи с обучением, валидацией и тестом v2, зафиксировать SHA-256. После выбора модели дать обеим версиям одинаковый набор. [Методика проверки](TRAINING_PLAN.md)
