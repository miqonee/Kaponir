# Полный отчёт: что показало исследование

Основные шесть схем завершены для всех семи моделей. Запланированные контроли
thinking, полного документа и одного кандидата на запрос тоже завершены.
Технически неполные профили отмечены отдельно и не получают общей оценки качества.

**Рабочее направление — сохранять предложения быстрых детекторов и дополнять
их поиском LLM. Автоматический отсев найденного по решению LLM пока ненадёжен.**
Некоторые более тяжёлые профили улучшили покрытие поиска. Проверка приватности
требует отдельного решения.


## Как читать решения и числа

| Термин | Понятное значение |
|---|---|
| Кандидат | Предложение проверить значение; это ещё не правило и не доказанная утечка |
| `mask` | Предложение скрыть значение заменой на анонимный токен |
| `keep` | Разрешение оставить значение открытым; для приватного эталона это ошибка |
| `review` | Сохранить на разбор: сомнение модели, конфликт или ошибка ответа |
| Тип | Что представляет значение: сумма, аккаунт, имя, путь и т. п. |
| Scope | Где применять правило: личный профиль, команда, компания; это не степень публичности |
| Вне эталона | Нет точного совпадения с разметкой; сюда входят частичные границы |
| Ошибочно отклонено приватных | Найденное приватное значение потеряно после `keep` |

В корпусе сравнивается точное значение внутри документа, повторы дедуплицированы.
Высокий процент обнаружения не доказывает верный тип, приватность или scope.

## Что и на чём проверяли

Общие данные — три синтетических документа: закрытая смета, журнал приложения
и публичная техническая справка. В них 92 точных приватных значения, включая
51 сумму. Исходные предложения детекторов содержат 68 эталонных значений
и 26 вне эталона. Значения вне эталона включают ошибки границ; считать все
их ложными срабатываниями нельзя.

Для каждой модели проверены: детекторы без LLM; добавляющий самостоятельный
поиск; проверка конкретных кандидатов; новый поиск в записях срабатывания;
один проверяющий проход по объединённому пулу; два прохода по тому же пулу.
Во втором проходе модель не видела ответ первого.

Общие токенные бюджеты — контекст 4096, выход 1600, temperature=0, thinking off.
Nanbeige использовала совместимый prompt-JSON, остальные — JSON Schema.
Gemma — QAT Q4_0, остальные — Q4_K_M. Большим моделям дали больше времени на CPU,
сохранив токенные бюджеты; запросы младших моделей завершились в прежнем таймауте.
Это сравнение конкретных рабочих профилей приложения.

Отдельные контроли использовали 32 кандидата с правильными границами — 16 приватных
и 16 публичных. Там отключена защита credentials, чтобы проверять саму LLM.
Проверялись также полный документ, ограниченное thinking и один кандидат на запрос.
Последний вариант сохранял общий контракт с типом и scope; чистый бинарный
«приватное / публичное» в этих опытах не изолировался.

## Основные результаты

Поиск показан как **эталонных из 92 / значений вне эталона**. Столбцы отклонений
считают приватные значения, уже найденные и затем ошибочно отброшенные проверкой.
Review сохраняет находку в очереди разбора, но не подтверждает её автоматически.
Один и два прохода в этой таблице проверяют объединённый пул конкретной модели
(`union_point` и `double`), а не только исходные предложения детекторов.

| Модель | Детекторы + поиск LLM | Отброшено приватных: один проход | Два прохода | На review после двух проходов |
|---|---:|---:|---:|---:|
| MiniCPM5-2B | 77 / 36 | 27 | 24 | 54 |
| Qwen3.5-2B | 80 / 51 | 57 | 0 | 112 |
| Huihui 2B | 76 / 66 | 42 | 5 | 117 |
| Qwen3.5-0.8B | 76 / 47 | 0 | 0 | 113 |
| Nanbeige4.2-3B | 89 / 69 | 20 | 15 | 94 |
| Granite4.2-3B | 79 / 26 | 21 | 5 | 85 |
| Gemma4 E4B QAT | 86 / 36 | 76 | 58 | 25 |

Ноль отклонений Qwen0.8 достигнут оставлением всех незащищённых кандидатов
на проверке. Qwen2 тоже сохраняет большой объём review. Эти нули не означают
успешную автоматическую разметку. Семь эталонных credentials и три предложения
вне эталона в основных схемах сохраняет защита независимо от решения модели.

Из 41 несуммового значения исходные детекторы предложили 17. Добавляющий поиск
Nanbeige сохранил 38, Gemma — 35, Qwen2 — 29, Granite — 28, MiniCPM — 26,
Qwen0.8 и Huihui — по 25. Высокий общий результат нельзя объяснить только суммами,
но 51 уже найденная детекторами сумма заметно облегчает общий счёт.

## Где получился полезный баланс

- **Granite, основной добавляющий поиск:** 79/92 и 26 вне эталона. Добавлены
  11 точных эталонных значений без увеличения числа значений вне эталона.
- **Nanbeige, основной добавляющий поиск:** 89/92 и 69 вне эталона. Наибольшее
  покрытие основной матрицы сопровождается увеличением очереди разбора.
- **Nanbeige, полный документ без thinking:** 86/92 и 31 вне эталона,
  все три документа завершены. Это другой профиль: 16384/4096, temperature=0.6.
- **Gemma, полный документ без thinking:** 84/92 и 27 вне эталона,
  все три документа завершены. К исходному пулу добавлены 16 эталонных значений
  и одно значение вне эталона. Профиль 16384/4096, temperature=1.
- **MiniCPM, полный документ без thinking в общем greedy-профиле:** 81/92
  и 29 вне эталона. Более крупная модель нужна не для каждого полезного поиска.
- **Детекторы + региональные находки Nanbeige:** 78/92 и 27 вне эталона.
  Добавляются десять эталонных и одно значение вне эталона. Это расчёт объединения
  сохранённых списков, без новых запросов; полная цепочка применения правил
  для такого объединения отдельно не запускалась.

Эти числа характеризуют кандидатные пулы. Тип, приватность и область применения
правила требуют отдельной проверки. Рекомендованные sampling-профили и большие
токенные бюджеты отделены от основной матрицы в [общих таблицах](TABLES.md).

## Полный документ и thinking: результат зависит от задачи

Ниже добавляющий поиск вместе с детекторами. Для младших моделей показан общий
greedy-профиль, для Nanbeige, Granite и Gemma — рекомендованный sampling.
Бюджет полного контекста — 16384, начальный выход 4096 с повтором до 8192 при
усечении, явный бюджет bounded thinking 2048. Это сравнение профилей; их sampling
различается между моделями.

| Модель | Без thinking: эталон / вне эталона | С bounded thinking |
|---|---:|---:|
| MiniCPM5-2B | 81 / 29 | 68 / 27 |
| Qwen3.5-2B | 74 / 33 | 77 / 32 |
| Qwen3.5-0.8B | 68 / 30 | 70 / 31 |
| Huihui 2B | не запускался | не запускался |
| Nanbeige4.2-3B | 86 / 31 | технически неполный, 1/3 документов |
| Granite4.2-3B | 76 / 26 | 75 / 27 |
| Gemma4 E4B QAT | 84 / 27 | 79 / 27 |

У MiniCPM рекомендованный sampling temperature=1 без thinking дал отдельно 72/29;
native thinking в том профиле завершил только один документ. Неограниченное
thinking Qwen и MiniCPM в отдельных контролях исчерпывало ответ без финального JSON.
Этим неполным профилям не присваивается нулевая точность.

У Gemma на одинаковых 32 кандидатах полного документа bounded thinking помогло
**проверке**: семь приватных mask, 16 публичных keep, девять ошибочных keep
приватного, ни одного review. У шести из семи mask верны одновременно тип и scope;
защита credentials в этом контроле отключена. Без thinking — ноль приватных mask,
14 публичных keep, 14 ошибочных keep приватного и четыре review.

Это пример, когда thinking полезно проверяющему и ухудшает покрытие поисковика.
Универсальное «всегда включать» или «всегда выключать» не подтвердилось.
23 верных действия из 32 у проверяющего Gemma выглядят как 72% общей точности,
но девять из 16 приватных значений ошибочно разрешены к раскрытию. Такая общая
оценка скрывает главную проблему автоматического отсева.

## Какие ошибки мы выделили

**Правильно назвать значение и решить, можно ли его раскрыть, — разные задачи.**
Gemma правильно назвала `1 320,00 ₽` суммой AMOUNT, но вернула keep и назвала
закрытую смету публичной. Восстановленный вход содержит запрет распространения.
Для этого случая исключены потеря статуса, обрыв ответа и OOM. Nanbeige при полном
контексте тоже ошибочно разрешила оставить `740,00 ₽`, назвав её единицей объёма.

**Модель иногда классифицирует соседний объект.** Nanbeige присвоила хосту
`cache01.cedar.test` тип SECRET и объяснила решение соседним паролем Redis.
Granite назвала цену FNAME, затем ORG. Нужны точная привязка к проверяемому
фрагменту и проверка каждого поля ответа.

**Два согласованных ответа одной модели могут повторять одну ошибку.**
Двойная проверка иногда уменьшает потери приватного по сравнению с одним проходом,
но увеличивает review и не обеспечивает достоверность. При оценке важны одновременно
ошибочные отклонения, правильность типа/scope и объём ручного разбора.

**Один кандидат на запрос тоже не дал универсального улучшения.** У MiniCPM
ошибочные keep приватного сократились с 12 до восьми, но ошибочные mask публичного
выросли с четырёх до пяти. У Qwen2 ошибочных keep стало четыре вместо трёх;
Qwen0.8 оставила все 32 случая на review. Здесь проверялся прежний совместный
контракт, а не отдельный короткий бинарный вопрос.

**Полный документ и thinking не дают универсального улучшения.** У Nanbeige часть
полных запросов с thinking достигла таймаута; OOM не зарегистрирован. У Granite
все полные запросы завершились, но thinking в проверке увеличило очередь review,
не дав применимых mask приватного по совместному контракту. Большой контекст
вместе с рекомендованным sampling дал Granite 75/27 или 76/26 против 79/26
основного поиска. Влияние каждого изменённого параметра отдельно здесь не измерялось.

**Техническая корректность и качество решений требуют разных проверок.**
У старого Qwen воспроизвели переполнение контекста при делении по байтам,
накопление отдельного RAM-архива и исчерпание ответа рассуждениями. Их разделили:
используется нативный подсчёт токенов с резервом, RAM-архив отключён, thinking
проверяется с явным бюджетом. Ошибочные keep сохраняются и в штатно завершённых
ответах. Завершённые основные прогоны Granite и Gemma не имели ошибок инференса.

## Предлагаемый следующий этап

1. **Явно задать политику анонимизации.** Различать «это сумма/логин/организация»
   и «это нужно скрыть в данном документе и проекте». Проверить, поможет ли
   доверенная политика вместо ожидания, что модель сама угадает критерий приватности.
2. **Сократить и уточнить вход.** Передавать статус документа, заголовки таблицы
   и нужную запись; явно отмечать проверяемый фрагмент. Проверить balanced-контекст
   с сохранением статуса и убрать повторение одной подсказки в каждом элементе пакета.
3. **Изолировать задачу проверки приватности.** Проверить короткий контракт
   mask/keep/review отдельно от типа, scope и цитирования. Сохранить действующие
   проверки до получения новых результатов: простое снятие ограничений может
   пропустить ошибочные keep.
4. **Доработать быстрые детекторы.** В замороженном пуле есть три защищённых
   ложных SECRET; LLM не может убрать их по протоколу. Даты, единицы, валюты,
   публичные идентификаторы и контекст путей стоит прежде обрабатывать детерминированно.
5. **Проверить выбранные связки на свежих документах**, затем выбирать профиль
   по умолчанию и встраивать его в интерфейс. Пока сохранять исходные предложения,
   использовать LLM для дополнения и разбора, а отклонения показывать пользователю
   как предложения. Пользовательские решения могут становиться правилами и данными S1.

Это гипотезы следующего этапа, а не уже измеренные улучшения. Для следующей
проверки поисковых связок я бы оставил Gemma без thinking (84/27), Nanbeige
без thinking (86/31) и основной поиск Granite (79/26); при ограничениях памяти —
MiniCPM без thinking (81/29). Эти кандидаты отвечают разным требованиям покрытия
и ресурсов. Перед выбором профиля по умолчанию нужна отложенная проверка.

## Границы выводов и исходные данные

Все семь моделей сравнивались на общих трёх документах с 92 значениями.
Полный корпус содержит восемь документов и 219 значений; все модели по нему
не прогонялись. Выбранный ранее добавляющий поиск Qwen2 на пяти отложенных
документах сохранил 79/127 и 58 вне эталона против 51/40 у детекторов.
Из сравниваемых локальных профилей только он проверен на всех восьми документах:
159/219 и 109 вне эталона.

Измеряются точные значения в списке находок, а не утечки после реального маскирования.
Scope — политика размещения правил бенчмарка; список реальных проектов пользователя
не передавался. S1 и пользовательские правила отключены; эксперименты не меняли
vault и обучение. Общего победителя SOTA и рейтинга скорости эти данные не устанавливают.

## Дополнительные результаты, важные для продолжения

### Сохранение конца контекста уже проверялось

На MiniCPM одинаковый point-прогон с 256 токенами подсказки дал:

| Политика подсказки | Осталось эталонных / 92 | Вне эталона | Приватных ошибочно отклонено из 68 предложенных | На review |
|---|---:|---:|---:|---:|
| Обычный prefix | 47 | 5 | 21 | 35 |
| Balanced, сохранены начало и конец | 57 | 8 | 11 | 44 |

Это измеренное улучшение контекста на калибровке: потерь на десять меньше, но очередь
разбора выросла и ошибки не исчезли. Для Nanbeige и Gemma отдельно проверяли только
видимость статуса при balanced через токенизатор, без новой генерации. Такой снимок
не доказывает улучшения решений этих моделей.

### Формулировка задачи меняет результат

У Huihui в ранних 12 калибровочных пробах исходная инструкция дала 6/12 верных действий
и 0/5 исправленных типов. Независимая классификация без подсказки исходного ошибочного
типа дала 10/12 действий и 5/5 типов. Это небольшая настраиваемая проба, с возможной
подсказкой в смысловых ID; она не заменяет позднюю общую матрицу.

### Внешняя модель тоже была проверена

Маршрут `ag/gemini-3.8-flash` отвечал идентификатором `gemini-3.8-flash-n`.
Идентичность базовой модели за шлюзом независимо не подтверждалась.

| Внешний опыт | Результат | Что показывает |
|---|---|---|
| Старая формулировка, восемь документов | 125/219, вне эталона 0 | Сильная модель могла резюмировать и пропускать значения |
| Смета: старая формулировка → перечислить каждое значение | 19/67 → 67/67 | Явное требование полноты помогло в этом опыте |
| Та же смета, полный документ → разбиение с целевым входом 4096 | 67/67 → 65/67 | Разбиение не является универсальным улучшением |
| Финальный поиск через настоящий API приложения, восемь документов | 192/219, предложено 194 | Две дополнительные находки отличались границами URL/hostname |

Это другой профиль: контекст 32768, выход 4096, `values`, до 128 кандидатов,
другой слой фильтрации и внутренние инструкции провайдера. Прямого рейтинга против
локальных 92-значных прогонов по этим числам делать нельзя. Старый клиент получал
Markdown/массивы/нестандартные типы и HTTP 503; эти сбои сохранены отдельно.
Дублирование схемы в инструкции исправило формат, а явное перечисление — полноту.
Внешний маршрут и параметры сохранены, рабочий ключ в пакет не включён.

### Внутренний классификатор измеряли отдельно

| Слой без S1 и пользовательских правил | Калибровка: эталон / вне эталона | Полные восемь документов: эталон / вне эталона |
|---|---:|---:|
| Сырые встроенные детекторы | 15 / 21 | 57 / 55 |

## Что уже исправлено в продукте, а что остаётся исследованием

Уже реализованы нормализация финансовых типов с запретом автоматического применения
исправленного ответа, раздельное отображение этапов/оценок, независимая формулировка
пересмотра без ошибочного исходного типа, сохранение пригодных фрагментов,
нативный расчёт токенного бюджета, отключение накопительного RAM-архива,
перенос пояснений в вопросники, улучшения разбора решений, установка моделей
и регистрация собственной GGUF по ссылке HF. История и регрессионные проверки
сохранены в [журнале сессии](SESSION_LOG.md).

Сравнение стратегий выполнялось в shadow-режиме. Найденный баланс поисковых профилей
не означает, что новая автоматическая политика отсева уже включена в продукт.
