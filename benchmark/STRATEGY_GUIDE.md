# Какие схемы полезны и с чего продолжать

Рекомендации по завершённому исследованию; новых прогонов этот документ не добавляет.
Все числа ниже относятся к сохранённым опытам. Проверка явной политики приватности
согласована пользователем как начало следующей сессии, но ещё не выполнена.

## Как читать результат

В поисковых таблицах `81 / 29` означает: в объединённом списке предложений есть
81 точное эталонное значение из 92 и 29 других значений. В исходном локальном
списке — **68 / 26**. Таким образом, этот профиль добавил 13 эталонных и три других.

Это оценка списка находок. Она не доказывает правильность типа, решения о приватности,
области правила или фактического маскирования всех вхождений. Среди других значений
бывают части приватных отрезков и ошибки границ; их нельзя все считать мусором.

«Осталось после проверки» включает `review` — ручной разбор. `Keep` означает
предложение оставить значение открытым; для приватного эталона это ошибка.
Ноль ошибочных keep при передаче всех случаев человеку не означает готовой автоматизации.

## Подходящие измеренные режимы по моделям

|---|---|---:|---|---|
| MiniCPM5-2B | Целый документ, thinking off, общий greedy-профиль | 81 / 29 | +13 эталонных и +3 других; кандидат при ограничении ресурсов | Balanced-подсказка помогла отдельной проверке, но ошибки сохранились |
| Qwen3.5-2B | Основной добавляющий поиск; альтернатива — целый документ с bounded thinking | 80 / 51; альтернатива 77 / 32 | Основной режим даёт больше находок; альтернатива — меньше других значений | Двойной проход дал 0 потерь приватного при 112 значениях на разборе; это не автоматический успех |
| Huihui Qwen3.5-2B | Основной добавляющий поиск | 76 / 66 | +8 эталонных и +40 других; преимущества перед остальными не показала | Надёжного автоматического отсева не получили; полного документного контроля не было |
| Qwen3.5-0.8B | Основной добавляющий поиск | 76 / 47 | +8 эталонных и +21 другое; полезные дополнения есть | В record-контроле и single-контроле все 32 случая остались на разборе |
| Nanbeige4.2-3B | Целый документ, thinking off, рекомендованный sampling | 86 / 31 | +18 эталонных и +5 других; основной режим даёт ещё выше покрытие 89 / 69 | Full/bounded технически неполон из-за таймаутов; его нельзя оценивать как нулевую способность |
| Granite4.2-3B | Основной добавляющий поиск | 79 / 26 | +11 эталонных, новых других значений нет; хороший измеренный баланс | Правильного применимого mask эталона вне защищённого обхода в основной матрице не получила |
| Gemma4 E4B QAT | Целый документ, thinking off, рекомендованный sampling | 84 / 27 | +16 эталонных и +1 другое; основной режим имеет покрытие 86 / 36 | Full/bounded: 7 приватных mask, 16 публичных keep, 9 ошибочных приватных keep; база следующего эксперимента |

Это разные профили, а не общий рейтинг моделей. Основная честно сопоставимая матрица
использует 4096/1600 и temperature=0. Полные профили используют 16384/4096 с retry
до 8192; у Nanbeige/Gemma здесь также рекомендованный sampling. Эти изменения
не изолируют влияние одного размера окна. «Целый документ» означает каждый из трёх
калибровочных документов целиком; все семь моделей на полном корпусе из восьми
документов не прогонялись. Точные параметры — [методика](METHODOLOGY.md).

## Что дали шесть схем

| Схема | Что делали | Вывод для продолжения |
|---|---|---|
| Локальные предложения | Встроенные детекторы + дополнительный локальный discovery без LLM | Сохранить как исходную базу; её собственные ошибки исправлять отдельно |
| Дополняющий поиск | LLM находит пропущенное, исходный список сохраняется | Самое полезное измеренное направление для выбранных профилей |
| Проверка исходных предложений | LLM решает, скрывать ли уже найденное, задаёт тип и scope | Автоматический keep пока часто теряет приватное; нужна новая постановка задачи |
| Перепоиск в записях срабатываний | LLM заново извлекает значения из релевантных строк/записей | Не заменять этим исходный список: метод создаёт новый пул; объединение с базой перспективно |
| Один проход по объединённому списку | Проверка предложений детекторов и найденного LLM | Наблюдались большие потери; у Gemma отброшено 76 уже найденных приватных значений |
| Два прохода по одному списку | Второй проход не видит ответы первого; решения сопоставляются | Иногда уменьшает потери, но одна модель повторяет ошибки; часто увеличивает ручной разбор |

Перепоиск по записям Nanbeige после объединения с исходным списком дал **78 / 27**:
+10 эталонных и +1 другое. Это расчёт по сохранённым результатам, без новых запросов
и без отдельной проверки всей цепочки применения правил. Его стоит проверить как
структурную альтернативу целому документу, сохраняя исходные предложения.

Один кандидат на запрос измерялся с прежним совместным контрактом. У MiniCPM
ошибочные keep приватного сократились 12→8, ошибочные mask публичного выросли 4→5.
У Qwen2 keep приватного выросли 3→4. Чистая короткая проверка приватности ещё не изолирована.

## Почему нужна новая постановка проверки

Gemma правильно назвала цену суммой, увидела статус закрытого документа и всё равно
разрешила оставить её открытой. Тип объекта и допустимость его раскрытия — разные
решения. Проверяющему нужна заданная приложением политика, а также точная цель вопроса.

Есть и технические ограничения совместного ответа: длинная причина, неправильный ID,
цитата или несовместимый тип оставляют review. Снятие ограничения длины объяснения
у Qwen пропускало и правильные, и ошибочные решения. Упрощение должно проверяться
новым опытом со своим валидатором, а не изменением подсчёта старых ответов.

## Следующая сессия: первый небольшой эксперимент

1. Прочитать [AGENT_HANDOFF.md](AGENT_HANDOFF.md), выполнить `python3 benchmark/verify.py`
   и проверить ветку. Исходные ответы и разметку оставить неизменными.
2. Описать версионированную политику внешней передачи документов: что делает данные
   непубличными и когда публичные сведения должны оставаться открытыми. Политика
   не содержит имён файлов, конкретных значений, ответов эталона или особых условий
   по имени модели.
3. Начать с Gemma, полный документ + bounded thinking: 32 контрольных случая,
   protected bypass выключен, сохранён профиль полного контроля с рекомендованным
   sampling. Текущие 9/16 ошибочных keep
   приватного — исходный уровень. Все ответы прошли формат, поэтому можно проверить
   семантическую гипотезу с меньшим влиянием ошибок формата.
4. Сравнить последовательно: **A** — исходный контракт; **B** — A + явная политика;
   **C** — B + явное выделение целевого отрезка; **D** — C + короткий ответ только
   ID, mask/keep/review и причина, без типа/scope/цитаты в этом этапе. D требует
   отдельного валидатора; тип и scope проверяются в отдельной задаче.
5. Между соседними вариантами сохранять модель, входные случаи, бюджет, thinking,
   sampling и seed. При изменении контракта менять только обусловленные им части.
   Записывать реальные запросы/ответы и хеши; эталон видит оценщик, а не LLM.
6. Считать раздельно ошибочные keep приватного, ошибочные mask публичного, review,
   применимость ответа и ресурсы. Не считать перевод всего в review улучшением
   автоматизации. После полезного результата проверить перенос на другую модель
   и новые документы.

Исходный полный контроль Gemma: контекст 16384, ответ 4096 с retry до 8192,
bounded reasoning 2048, temperature=1, top_p=.95, top_k=64, min_p=0, seed=42,
batch_size=8, timeout=1200 секунд; эффективный JSON-режим grammar. Это параметры
сохранённого сравнения, а не будущие обязательные константы продукта. Не подменять
этот профиль основным greedy-профилем при сравнении с сохранённым A.

Сохранённый A — доступная ссылка на исходный уровень, а не новая генерация.
Прежнюю обученную S1-модель не предоставляли, реальные проекты не передавали;
выводов об их качестве из этой матрицы нет. Область правила по возможности брать
из доверенного контекста; выбор проекта требует списка проектов и их ID.

## Предложения после первого эксперимента

- Сохранять статус документа, заголовки таблицы и целую логическую запись в компактном
  контексте. MiniCPM balanced уже уменьшил потери 21→11; для остальных моделей
  такую оценку решений ещё нужно сделать. В этом опыте review вырос 35→44,
  число подтверждённых эталонных значений осталось 13, а подтверждённых вне эталона
  выросло 4→8. Измерен выигрыш в сохранении кандидатов; автоматическая проверка
  от этого не стала надёжной.
- Исправлять известные ложные защищённые SECRET отдельной версией детекторов;
  сохранять прежний пул для сопоставимости LLM.
- Использовать LLM для дополнения и рекомендаций, показывать причины сомнений,
  сохранять исходные предложения до подтверждения отказа. Обучать S1 по подтверждённым
  решениям пользователя.
- После выбора профилей оценить новые документы и реальный mask→restore всех
  вхождений. Профиль по умолчанию выбирать после этой проверки.
