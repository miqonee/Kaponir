## Первый исследовательский блок

Начать с Gemma: полный документ + bounded thinking — все 32 ответа применимы
по формату, 7 приватных mask, 9 ошибочных keep. Это измеренная пригодная база
для проверки смысла задания, а не безопасный автоматический валидатор.
После полезного результата проверить перенос на Nanbeige или более лёгкую модель.

Предлагается последовательность с одной осью изменения на шаг:

| Вариант | Изменение |
|---|---|
| A | Существующий совместный контракт — зафиксированный baseline |
| B | Та же подача и выход, добавлена доверенная общая политика анонимизации |
| C | B + явная маркировка проверяемого отрезка в исходной записи |
| D | C + короткий выход только ID, mask/keep/review, короткая причина; тип/scope отдельно |

Это новые генерации с новыми profile ID и хешами. Подмена инструкций у кешированных
ответов запрещает научное сравнение. Сохранённый A можно использовать как проверенную
ссылку на baseline; нельзя выдавать его ответы за результат новых B/C/D.
Укорочение ID или переход к объекту с фиксированными ключами — отдельный следующий
опыт, чтобы не смешать эффект контракта и привязки ответов. ID остаются непрозрачными:
названия `price`/`login` подсказывают эталонную категорию.

Не снимать проверки со старых ответов ради роста числа mask: постобработка reason
уже показывала, что вместе с правильными ответами могут пройти ошибочные keep.
Новый узкий контракт требует своего валидатора и фактического парного опыта.

## Политика и проекты

Политика задаётся сценарием пользователя, например подготовкой внутреннего проекта
к внешней публикации. Различать тип сущности и допустимость её раскрытия.
Область правила по возможности брать из доверенного контекста приложения.
Для выбора реального проекта нужен список проектов и их ID; прошлый scope-бенчмарк
не проверял такой выбор. Не обучать S1 на неподтверждённых догадках LLM.

## Отдельный эксперимент контекста

Минимальный контекст: статус документа, релевантная запись, заголовки таблицы,
явно отмеченная цель. Общая подсказка передаётся один раз на пакет.
У MiniCPM balanced уже уменьшил ошибочные отклонения с 21 до 11 при тех же 256
токенах. Это не новый TODO повторить тот же опыт. Для Nanbeige/Gemma пока есть
только tokenizer-проверки видимости статуса, не matched-оценка решений с balanced.

## Критерии решения

Считать отдельно: ошибочные keep приватного, ошибочные mask публичного, review,
применимость контракта, правильность типа/scope, покрытие новых находок, количество
вызовов и ресурсы. Общая accuracy не является единственным критерием:
у Gemma 23/32 верных действия скрывают девять отклонённых приватных значений.
Нулевой private keep при всех review тоже не считается готовой автоматизацией.

До независимой проверки отклонения LLM остаются рекомендациями; исходные кандидаты
сохраняются, защитные правила имеют приоритет. Любой допуск к автоматическим
изменениям требует отдельного критерия и свежих данных, а не самооценки LLM.
