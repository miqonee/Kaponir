# Доработка качества и эксплуатации

[Документация](README.md) · [Текущее руководство](OPERATIONS.md) ·
[Архитектура](DESIGN.md)

> Исторический журнал изменений и проверок. Числа относятся к указанным датам;
> актуальные команды находятся в справочниках, а не в этом файле. Объёмные протоколы,
> HTML и логи сохранены в локальном `artifacts/`, который исключён из Git.

Цель: воспроизводимо закрыть пропуски повторного корпоративного аудита,
закрепить проверки в CI и добавить измеримую диагностику эксплуатации.

## Этапы

1. Регрессионный прогон 64 документов: полнота, публичные значения, точное восстановление.
   Расширение предложений discover; только явно выбранные предложения становятся правилами.
2. Исправление result_large_err без подавления Clippy; CI и проверка release-артефактов.
3. Метрики запросов, маскирования, восстановления и S1; измерения производительности.
4. Воспроизводимая оценка S1 на независимых данных и документация границ результата.

Серверный многопользовательский режим с ролями и общим vault — отдельный продуктовый
этап. Текущие контуры правил не следует представлять как многопользовательскую авторизацию.

## Исходное состояние

- cargo test --workspace: 98 успешных тестов.
- Clippy с -D warnings: 20 result_large_err в kaponir-proxy.
- Сохранённый аудит round2: 128 открытых значений / 1160 вхождений после правил,
  восстановление 64/64. Корпус синтетический, не независимый production-корпус.
- Проект не содержит .git и .github; удалённый CI здесь запустить невозможно.

## Решения

- Не маскировать произвольные числа автоматически: суммы и проекты предлагаются
  для подтверждения. Проверять весь сценарий настройки, а не только детектор.
- Не менять активность или пороги S1 на основании старого синтетического корпуса.
- Не обращаться к внешним моделям для проверки локальных изменений.

## Следующие шаги и ограничения

Нет независимого корпуса для подтверждения HTTP S1: запрос пути отправлен пользователю,
данные не предоставлены. Внешние запросы не выполнялись. Удалённый CI/macOS не запускались.
Общий многопользовательский сервер, роли и lifecycle ключей не реализованы этой доработкой.
Следующий этап качества — независимые данные и проверка реальной нагрузки с SQLite/S1.

## 2026-10-31: привязка сессий к ключам и переключение при 429

- `providers.rs`, `state.rs`: общий пул закрепляет сессию + модель + протокол за
  подключением. Новые сессии распределяются стабильным хешированием. Привязки ограничены
  8192 записями, временем простоя и проверкой актуальной доступности подключения.
- `server.rs`: при HTTP 429 повторяются те же замаскированные байты с другим подходящим
  ключом. Каждый ключ используется максимум один раз в запросе. Последняя попытка
  отражается в connection_id события; исчерпание возвращает последний 429 с Retry-After.
  Отдельные адреса, сетевые ошибки, другие HTTP-ошибки и начатые SSE не переключаются.
- `tests/proxy.rs`: параллельные запросы одной неявной сессии сохраняют ключ; сквозной
  тест для OpenAI и Anthropic проверяет явный ID, 429, SSE-восстановление, идентичность
  повторяемого тела, HTTP 500, исчерпание, отдельный адрес и удаление привязанного ключа.
- `assets/providers.js`, `assets/locales/{ru,en}.json`, `CONTROL_PANEL.md`: обновлены
  объяснения, примеры SDK с X-Kaponir-Session и ограничения определения сессии.
- Проверено: cargo test --workspace (120), cargo clippy --workspace --all-targets --
  -D warnings, cargo fmt --all -- --check, node --check providers.js, 2 locale-теста.
  Debug CLI собран. Форма и тексты RU/EN открыты встроенным браузером через временный
  сервер с фиктивным локальным подключением. Реальные поставщики не вызывались.
- Ограничения: изменения привязки после 429 не переживают перезапуск/вытеснение/истечение
  простоя; общего карантина ключа и ожидания Retry-After нет. Эти свойства документированы.
