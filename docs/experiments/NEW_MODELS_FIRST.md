# Сначала новые модели на уже проверенном протоколе

17 ноября 2026 года пользователь уточнил порядок: использовать накопленный корпус
семи моделей и подобранные prompts, сначала проверить восемь новых вариантов.
Массовый повтор прежних семи не требуется. Подготовленный проект такого повтора
отменён до регистрации и запуска; он не попал в Git и не сделал модельных вызовов.

## Что уже есть

Архив содержит все шесть схем для семи моделей: 42 результата на трёх прежних
синтетических документах. Их SHA, разметка, детекторный пул и оценки проверяются
без новой генерации. A–D полностью наблюдены у шести старых моделей после
дополнений транспорта; у Nanbeige в этой отдельной серии ответы ещё отсутствуют.
Свежие RU/EN — следующий этап проверки переноса, не основание повторять старый корпус.

Подбор prompts сохраняется. D — текущий лучший вариант Gemma для решения о
приватности заранее найденных целей. Перепоиск записей — отдельная задача;
в архиве здесь выделяется Nanbeige. Это разные контракты, их таблицы не объединяются.

## Первый полный прогон новых восьми

Выбран существующий протокол `nanbeige-calibration--result.json.gz`: все шесть
прежних схем, те же документы, детекторный пул, PRIMARY/AUDIT/REGION prompts,
prompt извлечения, типы и разметка. Выбор сделан по прежнему результату перепоиска,
не по ответам новых моделей на свежих документах. Приватность и правила заново
для каждой модели не подстраиваются.

| Параметр | Значение существующей опоры и новых запусков |
|---|---|
| Контекст / ответ | 4096 / 1600 токенов |
| Повтор с большим ответом | Нет |
| Temperature / top-p / top-k / min-p | 0 / 0,95 / 40 / 0 |
| Seed | Не передаётся, как в архиве |
| JSON | Записанный исходный `auto`: grammar при поддержке runtime, иначе схема в инструкции |
| Thinking | Запрошен off; фактический шаблон и возвращённое reasoning проверяются отдельно |
| Ожидание HTTP и timeout Worker | 1200 / 1200 секунд |
| CPU / слоты / GPU | 2 / 1 / 0 |
| Runtime | Тот же закреплённый SHA `3e042c…` |

Совпадает протокол запросов. Лимит прежнего контейнера составлял 2 CPU / 8 GiB,
текущего — 4 CPU / 16 GiB; оба runtime используют два потока. Это различие уже
зафиксировано в [общем протоколе](PRIVACY_POLICY_PHASE2.md#замороженный-профиль)
и не позволяет приписывать разницу времени только модели. Фактическое соблюдение
thinking отдельно проверяется по встроенному шаблону и полученному ответу.

Таблица ресурсов показывает префикс рассуждения в сформированном запросе и
рассуждения в фактических ответах. В запрошенном режиме `off` шаблон
LFM2.5-8B-A1B сформирован без префикса. Модель вернула рассуждения в первых
семи измерительных ответах. Шесть из них исчерпали лимит 1600 токенов.
В отчёте указано число ответов, для которых сохранена соответствующая телеметрия.

Для LFM2.5-2.6B условие off оказалось невыполнимым: GGUF безусловно добавляет
`<think>` и не использует `enable_thinking`; on/off-пробы совпадают. Попытка
остановлена после получения двадцатого ответа, все 20 транспортов и затраты
сохранены. Это диагностика несовместимости, не полный результат шести схем
и не нулевые ошибки модели. В исправленной очереди несовместимость определяется
до обращения к корпусу; двадцать прежних ответов сохраняются отдельно.
Следующий обязательный опыт этой модели — полный прежний Gemma A/B/C/D,
где reasoning разрешён и ограничен. Подготовленный D32 сохраняется как подготовка,
но не заменяет все четыре варианта. Старый Gemma повторно не запускается.

В текущем `main` добавлен ранний отказ до первого измерительного запроса,
если нативный шаблон при запрошенном off всё равно принудительно открывает
`<think>`. Совпадение on/off-хешей само по себе не является отказом: у моделей
без thinking оба шаблона тоже могут совпадать. Сохраняются план и диагностика,
существующие измерения защищены от перезаписи. Прежний замороженный producer
`9c28368` и его диагностические попытки сохраняются без изменений.

Сохранён и прежний алгоритм окон и префиксов. Это полный прежний набор документов
и схем, а не выдача всего документа одним запросом. Токенизатор и chat template
являются свойствами самой модели; их хеши и фактические размеры входа фиксируются.
Фоновая проверка GGUF может ждать до 600 секунд до запуска runtime; это подготовка,
она не продлевает измерительный HTTP-бюджет. Исправление устраняет ложный отказ
после 30 секунд проверки большого файла.

Сверка обнаружила ошибку первой очереди новых моделей: из архива был скопирован
фактически выбранный Nanbeige fallback `prompt`, хотя исходный запрос содержал
`auto`. У старых Gemma, Granite и Nanbeige совпадают записанный исходный `auto`,
входы, лимиты и sampling; runtime выбрал grammar, grammar и prompt соответственно.
Исправленная очередь `new-models-reference-v2` повторяет именно исходный выбор.
Завершённый LFM1.2 и начатый Tiny Aya из v1 сохраняются как отдельные попытки
с принудительным prompt и повторяются только на этих новых моделях. На момент
исправления остальные пять новых вариантов ожидали полного корпуса.

Старые архивы содержат и другие настройки: у Qwen/Huihui ожидание было 300 секунд.
У раннего MiniCPM
не все метаданные sampling/JSON явно записаны. Это точечный пробел метаданных,
а не отсутствие всего проверенного корпуса. Поэтому прямой совпадающий профиль
первого этапа — архивные Gemma, Granite, Nanbeige и новые восемь; остальные прежние результаты
показываются со своими настройками. Единый строгий профиль всех 15 не заявляется.
Если дальнейший вывод зависит от другого архивного режима, повторить его можно
на нужной новой модели, сохранив прежнюю опору.

Сохранённые результаты и фактическое применение собраны в
[сравнительной таблице](NEW_MODELS_RESULTS.md). Она заново читает старые ответы,
не повторяя генерацию, и показывает все шесть схем, технические отказы,
покрытие всех вхождений и справочные ресурсы.

| Схема | Что проверяет |
|---|---|
| Детекторы | Исходный список предложений встроенных детекторов |
| Добавляющий поиск | Поиск моделью по документу и объединение с исходным списком |
| Проверка списка | Решения модели по предложениям встроенных детекторов |
| Перепоиск записей | Извлечение значений из записей, в которых сработали детекторы |
| Проверка объединения | Решения модели по исходным и добавленным предложениям |
| Два прохода | Проверка объединения и отдельный аудит этого списка |

## Исполнение и отчёт

После шести схем обязателен полный парный A/B/C/D для каждой новой модели,
включая собственный A: 32 прежние цели × четыре варианта, 128 исходов на модель,
1024 исхода на новые восемь. Малый срез B/D и подготовленный D32 не заменяют
этот опыт. Профиль нового блока повторяет сохранённую Gemma A/B/C/D: контекст
16384, ответ 4096, предусмотренный повтор до 8192, reasoning budget 2048,
temperature 1, top-p 0,95, top-k 64, seed 42, grammar и timeout 1200 секунд.
Сохраняются исходные 32 случая, политика v1, prompts, schemas и порядок пакетов.

`run_reference_abcd.py` готовит ровно восемь новых моделей. Флаг
`--paired-reference` проверяет совпадение всех тел запросов с архивной Gemma,
кроме имени модели, как при подготовке, так и после реального подсчёта токенов.
Если прежние пакеты не помещаются, иной режим не подбирается: сохраняется N/A
без обращения к корпусу. Разрешённые ограниченные рассуждения в этом блоке
позволяют отдельно проверить LFM2.6, несовместимую с off в шести схемах.
Очередь ждёт окончания всех восьми попыток шести схем и 48 применений;
параллельные модельные runtime не запускаются. У шести старых моделей A–D
уже получены, у старой Nanbeige сохраняется отдельный пробел ответов.

По уточнению пользователя LFM2.6 сохраняется обязательной последней моделью
полного A/B/C/D. Порядок: LFM1.2, Tiny Aya, Qwen4B, Spark, LFM8B-A1B,
Gemma E2B-it, Gemma E4B-it, LFM2.6. Для LFM2.6 здесь разрешены ограниченные
рассуждения; несовместимость с off из шести схем не считается исключением
из исследования. Переставляется только порядок моделей, все A–D и запросы
сохраняются. Уже работающая очередь шести схем не перезапускается.

Отчёт A/B/C/D связывает исходы каждой из 32 целей с результатами применения
выбранной маскировки к трём документам. В CSV нужны и число ошибок запросов,
и число целей с непригодными решениями. Сохраняются пропуски, ручная проверка,
потери публичных вхождений, время, CPU и наблюдённая память. Команда отчёта
использует сохранённые ответы и результаты API.

```sh
python scripts/report_reference_abcd.py --output /tmp/kaponir-abcd-report
```

`run_legacy_new_models.py` допускает ровно восемь новых ID. Уже завершённый
малый срез принимается без повтора; его 1536/512 и нативные sampling не подаются как равные
архивному протоколу. Три зарегистрированные короткие диагностики
Nanbeige уже получены и принимаются по сохранённым SHA без повторной генерации.
Затем идут восемь полных запусков на прежнем корпусе. Диагностика времени
Nanbeige не является повтором его полного benchmark.

Прежняя расширенная очередь 69 заданий отложена до анализа этого этапа.
Её producers, команды и полученные данные сохранены. Новые свежие случаи,
парные политики и нативные профили остаются последующими отдельными проверками.
Неопределённая отправка не повторяется автоматически; полученные ответы не исправляются.

Подготовка без генерации:

```sh
python3 scripts/evaluate_model_schemes.py --prepare-only \
  --model lfm2.5-1.2b-instruct --profile common \
  --legacy-reference nanbeige42-3b --output /tmp/kaponir-reference-prepared
```

План связывает архивные и исходные SHA. Любое расхождение текстов, типов,
разметки, детекторного пула, sampling, лимитов или JSON-режима блокирует повтор
протокола. Отчёт заново оценивает сохранённые старые ответы и новые результаты,
разделяет сопоставимую опору и другие исторические профили. Время и ресурсы
остаются справочными; фактическое mask→restore проверяется отдельным этапом.
