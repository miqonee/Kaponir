## Сценарий и проверяемая гипотеза

Приложение готовит документ к передаче внешнему получателю, которому не разрешено
получать частные персональные, проектные и деловые сведения. Проверяющая модель
решает, допустимо ли оставить открытым **точное целевое значение в этом контексте**.
Тип сущности и разрешение на раскрытие — разные вопросы. Например, правильное
распознавание финансового значения ещё не устанавливает его публичность.

Гипотеза: заданная приложением политика уменьшит ошибочные `keep` приватного;
явная привязка к отрезку и затем короткий контракт могут отдельно помочь этой
задаче. Ожидаемый эффект не считается результатом до новых запросов.

Доверенная английская политика хранится в [privacy-policy-v1.txt](privacy-policy-v1.txt)
и передаётся модели дословно. Файл заморожен до новых генераций. Его SHA-256:

```text
a6ce52bb481ae186d81c00e1df0d1171ebac91834e16c59b45fce0e2f1d6a144
```

Политика составлена по сценарию передачи и опубликованному описанию задачи,
без отдельного чтения полного контрольного пула и его разметки. Некоторые ошибки
и конкретные примеры уже известны из прежнего отчёта; это не слепая разработка
политики на невиденных данных. Политика не
содержит имён файлов, конкретных значений, ответов эталона или условий по модели.
Закрытый статус не делает каждый общий термин приватным, а публичный статус
не разрешает раскрывать случайно попавшие в документ действующие секреты.
Документ предоставляет контекстные факты, но не может переопределять политику.
После просмотра новых ответов правка политики требует версии v2 и нового каталога.

## Порядок сравнения и выбор подхода

Пользователь уточнил 15 ноября: стандартные ставки и общеизвестные технические
названия остаются открытыми и в рабочих документах, если отдельно не указана
конфиденциальность самого выбора. Например, закрытая цена маскируется, стандартная
ставка НДС сохраняется. Это подтверждает исходные метки трёх пограничных контролей;
разметка и замороженный текст политики/запросов не менялись. Смысловой разбор —
[общие ситуации](PRIVACY_RULE_REVIEW.md) и
[совместимость эталона с политикой](CALIBRATION_POLICY_COMPATIBILITY.md).

Политика общая для всех моделей. Сначала разбираются её смысл и спорные случаи,
затем выполняется полный опыт A/B/C/D на **всех семи ранее протестированных
вариантах**. Gemma — первый запуск. Для MiniCPM5-2B, Qwen3.5-2B,
Huihui Qwen3.5-2B, Qwen3.5-0.8B, Nanbeige4.2-3B и Granite4.2-3B также
сравниваются все четыре задания на тех же 32 контролях. Для Qwen сохраняется
полный парный опыт; перенос только лучшего задания Gemma его не заменяет.

После выбора подхода проверяется перенос на свежие документы. Затем сравнение
расширяется шестью новыми моделями из [плана расширения](../../benchmark/MODEL_EXPANSION_PLAN.md):
общий целевой набор содержит 13 вариантов. Подготовленные профили, запланированные
запуски и полученные результаты должны иметь разные статусы.

Основной критерий выбора — качество проверки приватности: ошибочное раскрытие
приватного, ошибочное скрытие публичного, применимость ответов и объём ручного
разбора. Вариант со всеми случаями в `review` не считается готовой автоматизацией.

Время и ресурсы имеют низкий приоритет и сохраняются главным образом для справки
и подбора под железо. Они помогают выбрать среди вариантов с сопоставимым качеством
или проверить выполнение конкретных ограничений устройства. Выигрыш в скорости
или памяти не компенсирует ошибки приватности; ресурсные показатели не включаются
в оценку качества.

## Данные и четыре варианта

Используются существующие 32 контрольных случая с правильными границами:
16 приватных и 16 публичных. Отбор уже зафиксирован в
`tests/fixtures/context-control-candidates.json`; это прежний диагностический пул,
а не новые невиденные документы. Защищённый обход credentials выключен во всех
четырёх вариантах. Разметка и эталонные типы доступны только оценщику.

Единица оценки — пара «документ, точное значение». Повторы в одном документе не
становятся независимыми наблюдениями. ID остаются непрозрачными; модель не получает
исходный тип, вероятность детектора или метку приватности.

| Вариант | Вход и контракт | Единственное изменение относительно предыдущего |
|---|---|---|
| A | Полный документ, исходная запись, исходный совместный контракт | Новая генерация исходного профиля без политики и маркировки |
| B | То же, с политикой v1 в доверенной инструкции | Добавлен дословный текст политики |
| C | B с дополнительным `marked_record` для каждого ID | Явно выделен проверяемый отрезок в записи |
| D | Контекст C, ответ только `id`, `verdict`, `reason` | Более короткие инструкция, схема и валидатор без type/scope/evidence |

По умолчанию **все A/B/C/D генерируются заново**. Совместный контракт A–C
содержит `id`, `verdict`, `kind`, `scope`, `evidence`, `reason` и сохраняет прежние
проверки. `verdict` имеет значения `mask`, `keep`, `review`. В D тип и scope
не предсказываются, не восстанавливаются оценщиком и не объявляются проверенными;
их независимая проверка — отдельная задача.

Полный документ и исходное поле `record` в C/D не переписываются. Дополнительная
маркированная запись указывает конкретное вхождение через непрозрачный ID.
Координаты `start:end` — индексы Unicode-символов Python-строки исходного документа;
до подготовки проверяется точное равенство `document[start:end] == value`.
Маркеры не добавляют категорию, ответ или объяснение чувствительности.
При повторениях фиксируется выбранное исходное вхождение, а не произвольный
повторный поиск подстроки. Проверка разметки и экранирования должна исключать
конфликт исходного текста с маркерами.

У C появляется дополнительное поле и дополнительные токены: это эффект явной
привязки в выбранном представлении, а не доказательство преимуществ любого способа
маркировки. У D одновременно сокращается генерация и число условий применимости.
Его эффект следует описывать как эффект короткого контракта, не приписывать
весь выигрыш одному удалённому полю.

## Замороженный профиль

Первый запуск использует Gemma4 E4B QAT Q4_0 с тем же закреплённым GGUF-артефактом,
что и исторический полный контроль. Модель и runtime проверяются по SHA-256;
идентичность не устанавливается одним именем файла.

Таблица ниже задаёт начальный профиль **Gemma**. Для каждой другой модели до
генерации фиксируется отдельный профиль с её нативными возможностями и
ограничениями. Внутри её A/B/C/D одинаковы артефакт, контекст, бюджеты ответа и
thinking, sampling, seed, потоки и политика повторов. Параметры sampling Gemma
не переносятся на остальные модели автоматически. Общие профили сравнения и
рекомендованные профили конкретных моделей показываются отдельно.

| Параметр | Значение |
|---|---|
| Контекст | 16384 токена, полный документ без скрытого усечения |
| Начальный ответ / повтор при усечении | 4096 / до 8192 токенов при наличии места |
| Резерв контекста | 64 токена |
| Thinking | Включён, нативный bounded budget 2048 |
| Sampling | temperature=1, top_p=0.95, top_k=64, min_p=0, seed=42 |
| Пакет | До 8 кандидатов, общий состав и порядок для A/B/C/D |
| Timeout | 1200 секунд на запрос |
| Структурный ответ | JSON Schema / grammar |
| Runtime | llama.cpp; исполняемый файл закреплён ожидаемым SHA-256 |
| Исполнение | CPU, 2 потока, 1 слот; `cache_prompt=false` |

Среда текущей подготовки имеет CPU quota 4 и 16 GiB RAM; прежнее исследование
использовало CPU quota 2 и 8 GiB RAM. Число потоков runtime остаётся равным 2,
но различие машины всё равно фиксируется в provenance. Время и память старой
и новой сессии не дают прямого рейтинга скорости.

Перед первым запросом нативный tokenizer с фактическим chat template проверяет
все варианты. Если хотя бы один вариант пакета не помещается, общий пакет делится
для **всех** A/B/C/D; новый общий план сохраняется до генерации. Нельзя сократить
документ, незаметно сменить состав пакетов только у C/D или сравнить разные
reasoning-бюджеты. Предварительный план `--prepare-only` не заменяет эту проверку.
Один seed и один запуск не доказывают устойчивость модели.

Изменение модели, runtime, политики, prompts, schema, tokenizer/template, бюджета,
sampling или плана пакетов после начала вызовов требует нового профиля и каталога.
Продолжение прерванного запуска допускает только совпадающую signature. Повторы
разрешены по заранее заданной технической политике, не для выбора лучшего ответа.

## Историческая опора A

Сохранённый Gemma full/bounded дал 7 приватных `mask`, 9 ошибочных приватных `keep`,
16 публичных `keep`, `review=0`; у 6 из 7 `mask` одновременно верны тип и scope.
Это историческая ссылка, а не новая генерация. Исходные ответы не прогоняются через
новый валидатор под видом новых измерений.

Прямое сравнение нового A со старым допускает вывод о совместимости только после
сверки GGUF, runtime, template/tokenizer, источников, случаев, prompts/schema,
sampling, budgets и разбиения пакетов. Различие необходимо явно указать. Основные
выводы этапа строятся по новым соседним парам A→B, B→C, C→D в одном общем профиле.
Даже при совпавшей конфигурации новый ответ со стохастическим sampling не обязан
дословно повторить исторический.

## Валидатор D и ошибки

Для D используется отдельный валидатор, а не ослабление проверок старых ответов:

- Корректный JSON без повторных ключей и посторонней структуры.
- Каждый ожидаемый ID присутствует ровно один раз; неизвестные ID не допускаются.
- У решения только `id`, `verdict`, `reason`; `verdict` — `mask`, `keep` или `review`.
- `reason` — строка не длиннее 120 Unicode-символов.
- Никаких требований к отсутствующим `kind`, `scope`, `evidence` и никакой
  автоматической подстановки их значений.

HTTP/JSON-сбой, timeout, усечение без пригодного ответа или неприменимая запись
не превращаются в семантический `keep`. Технический разбор отделяется от явного
`review` модели. Завершённость протокола и качество выданных решений читаются
раздельно; незапрошенные случаи не получают оценку как ответы модели.

## Артефакты и метрики

Новые файлы находятся только в `artifacts/privacy-policy-phase2/<profile-id>/`.
Результаты не дописываются в старые `benchmark/data/` и контрольные архивы.
Сохраняются действительные запросы и ответы, порядок вызовов, причины повторов,
технические статусы и план пакетов. `prepared` означает подготовку без измерения.

Signature должна связывать Git HEAD и хеши исходников экспериментального кода,
runtime/model/template, исходных документов, случаев и эталона, политики, каждого
prompt/schema/validator, параметров sampling/thinking и общего плана запросов.
После нативной проверки сохраняются фактические input tokens и лимиты ответа.
Эталон не передаётся модели, даже если его hash входит в provenance.

Для каждого варианта и каждой соседней пары отдельно показываются:

- ошибочные `keep` приватного из 16 и ошибочные `mask` публичного из 16;
- корректные действия, явный `review`, технический разбор, число применимых ответов
  и число запрошенных/незапрошенных случаев;
- переходы конкретных ID: например `keep→mask`, `keep→review`, а также регрессии;
- у A–C правильность типа/scope с явным знаменателем; у D эти поля неприменимы;
- зарегистрированные попытки запросов, подтверждённо полученные ответы, сбои,
  прерванные попытки с неизвестным фактом отправки и повторы; отдельно —
  токены входа/ответа/reasoning, время, память, runtime errors и завершённость.

Запрос фиксируется в checkpoint до отправки. Если процесс прерван между этой
записью и сохранением ответа, нельзя точно знать, был ли запрос физически отправлен
или выполнен сервером. Такая запись учитывается как неопределённая попытка,
не как подтверждённая генерация; сохранённый pending-запрос автоматически
не отправляется повторно. Проверки возможностей runtime считаются отдельно от
запросов на 32 контрольных случаях.

После подтверждённого исчезновения владельца и освобождения runtime допустима
отдельно зарегистрированная новая попытка в новом каталоге. Прежний pending
сохраняется с неизвестным исходом. Продолжение связывает SHA исходного checkpoint,
переносит полученные ответы побайтно и заново проверяет их прежним валидатором.
Ранее полученные неверные ответы также сохраняются. Если стоимость прежней
попытки неизвестна, полный итог HTTP остаётся пустым: таблица показывает известные
секунды и число попыток без замера. Ресурсы прежней сессии учитываются, когда они
сохранены; отсутствие замера не превращается в нулевую стоимость.

Для экспорта после смены среды реестр выходов указывается явно через
`scripts/export_privacy_snapshot.py --recovery-queue PATH/queue.json --output NEW_PATH`.
Исходный реестр не редактируется. Архив включает checkpoint продолжения и его
исходный checkpoint; `--verify NEW_PATH --rescore` повторно проверяет сырые ответы
даже при недоступности первоначальных каталогов.

Общая accuracy не заменяет эти показатели. Ноль private keep при передаче всех
случаев человеку не означает готовую автоматизацию. Время на общей машине и
единственный seed не образуют надёжный рейтинг скорости или качества.
32 уже известных контроля дают диагностический результат; после полезного эффекта
нужна проверка другой моделью и на новых документах, затем реального mask/restore.

## Время, ресурсы и подбор под железо

Измерение времени и ресурсов обязательно для каждого нового запуска и каждого
варианта A/B/C/D. Обязательность сбора не повышает их приоритет при выборе:
это преимущественно справочные показатели с низким весом относительно качества.
Следующие пункты задают контракт нового сбора телеметрии;
они не являются уже полученными показателями качества или скорости. Исторические
архивы сохраняют исходную детализацию и не дополняются выдуманными измерениями.

Вместе с результатом сохраняется описание машины и профиля:

- модель CPU, доступные логические/физические ядра, affinity процесса и лимит CPU
  контейнера; доступные RAM/swap и лимит памяти контейнера;
- ОС, архитектура, kernel, точные модель/runtime и их хеши, квантование и размер
  файлов модели на диске;
- контекст, входные и выходные токены, thinking, batch, потоки, слоты, лимиты,
  настройки кеша и фактический режим исполнения.

Текущий стенд использует CPU без offload на GPU. Потребление VRAM и скорость
GPU в нём не измеряются. Число ядер хоста не подменяет лимит CPU контейнера или
affinity. Описание машины не включает имя хоста, пользователя и секреты.

### Границы времени

Сохраняются отдельные интервалы загрузки/готовности процесса runtime, проверки
возможностей и планирования, каждого HTTP-запроса, варианта и всей сессии.
Повтор после усечения входит в стоимость варианта и полного запуска, даже если
последующий ответ оказался пригодным. Загрузка/проверка файлов и прочая подготовка
показываются отдельно от собственно обработки 32 случаев. При возобновлении
интервалы отдельных сессий и периоды без активной работы различаются.

Время до готовности runtime включает запуск процесса, загрузку модели и проверки
готовности, предусмотренные движком. Отдельные пересекающиеся интервалы не
складываются повторно. Запуски и повторное использование готового процесса
различаются. Название «холодный запуск» допускается только при контролируемом и
записанном состоянии файлового/OS-кеша; новый процесс сам по себе этого не доказывает.
Политика runtime-кеша также фиксируется независимо от OS-кеша.

Нативные `timings` движка позволяют отдельно показать скорость обработки prompt
и скорость генерации (`native_prompt`, `native_prediction`). Если их нет,
сохраняется явно обозначенная скорость всех completion-токенов за полное время
HTTP-запроса (`throughput.whole_request.completion_tokens_per_second`). Она включает ожидание и
обработку входа и не выдаётся за скорость decode. В текущем нестриминговом режиме
TTFT не измеряется: `ttft_seconds=null`, а полное время ответа не называется
временем до первого токена. Токены reasoning и финального ответа учитываются
согласно фактической телеметрии runtime с указанием недоступных полей.

### Память, CPU и технические ограничения

Во время интервала выполняются периодические замеры. Сохраняются частота, число
замеров, ошибки и недоступные показатели. Процессы worker, модели и OCR учитываются
раздельно; PID вместе со временем создания процесса позволяет различать перезапуски.
Для каждого процесса доступны начальный/конечный RSS и наблюдавшийся пик
`observed_peak_rss_bytes`, CPU user/system seconds и среднее число занятых ядер
`average_cpu_cores`. `average_cpu_percent_one_core` рассчитан относительно одного
ядра и может превышать 100%; это не процент от всей машины.

Наблюдавшийся пик RSS зависит от интервала выборки. Он не гарантирует точный
кратковременный максимум и не равен минимальной RAM, достаточной для другого
устройства. RSS нескольких процессов может учитывать общие страницы повторно.
Контекст, KV-кеш, batch, квантование, резерв ОС и одновременная нагрузка также
влияют на требования к памяти.

Отдельно сохраняются начальные/конечные показатели cgroup, наблюдавшийся пик
`memory.current`/swap и изменения счётчиков OOM. Показатель `memory.peak` cgroup
может относиться ко всей жизни контейнера; его нельзя приписывать конкретной
модели или запросу. Контейнерные измерения описывают всю нагрузку контейнера,
поэтому они не заменяют показатели отдельного процесса модели. Отсутствующий
метрический источник отмечается явно и не превращается в нулевое потребление.

Timeout, OOM, ошибки runtime и неполные ответы показываются вместе с качеством и
ресурсами. Вариант, не завершивший обработку, не становится быстрым успешным
профилем за счёт пропущенных случаев. Время на общей машине и сравнение разных
конфигураций описываются как наблюдения в указанных условиях.

### Сводная таблица для выбора

В отчёте одна строка соответствует модели, варианту задания и профилю запуска.
Сначала варианты оцениваются по качеству. Справочные столбцы времени и ресурсов
помогают подобрать железо и различить варианты с сопоставимым качеством:

| Группа столбцов | Обязательные значения |
|---|---|
| Модель и профиль | Артефакт, квантование, размер на диске, CPU/лимиты RAM, контекст, потоки, batch, thinking |
| Качество | Private keep, public mask, корректные действия, явный review, технический разбор и применимость с отдельными знаменателями |
| Готовность | Время запуска/готовности runtime и проверок отдельно от обработки случаев; повторное использование процесса |
| Задержка и стоимость | Время каждого запроса, медиана/максимум и число наблюдений, время варианта и всей сессии, все повторы |
| Скорость токенов | Нативные prompt/decode токены/с либо явно обозначенная скорость completion за полное время запроса |
| Память | Наблюдавшийся пик RSS модели, worker/OCR отдельно, наблюдавшаяся память контейнера, интервал замеров |
| CPU | User/system seconds, средние занятые ядра и процент относительно одного ядра, лимит CPU и affinity |
| Надёжность | Завершённые случаи, timeout/OOM, сбои, повторы, неопределённые прерывания и статус полноты |

Одна машина даёт измерения для своей конфигурации. Для рекомендаций под другое
железо нужны соответствующие прогоны; измеренный RSS служит ориентиром с указанными
условиями, а не точной универсальной границей памяти.

## Воспроизведение

Команды выполняются из корня репозитория. Быстрая подготовка не скачивает веса,
не запускает runtime и не делает LLM-запросов:

```sh
python3 benchmark/verify.py
python3 scripts/evaluate_privacy_policy.py --help
python3 scripts/evaluate_privacy_policy.py \
  --prepare-only \
  --output artifacts/privacy-policy-phase2/gemma-new-profile
```

Для нативной проверки и фактического запуска заранее подготовить закреплённые
GGUF и `llama-server`. Пути ниже следует заменить реальными абсолютными путями.
Промежуточная проверка загружает модель и проверяет реальные chat template,
tokenizer, общий план пакетов и бюджеты всех вариантов:

```sh
python3 scripts/evaluate_privacy_policy.py \
  --preflight-only \
  --model-dir /absolute/path/to/models \
  --runtime /absolute/path/to/llama-server \
  --output artifacts/privacy-policy-phase2/gemma-new-profile
```

`--preflight-only` не выполняет измерений на 32 случаях: число таких запросов
остаётся нулевым. При запуске runtime проверка поддержки JSON Schema генерирует
крошечные ответы на служебные запросы без контрольных данных. Эти capability
probes явно учитываются отдельно; поэтому этот режим нельзя описывать как полное
отсутствие LLM-генерации. Проверка сохраняет `preflight.json`, хеши нативных
template probes и проверенный общий `plan.json`.

Та же папка подготовки может использоваться для фактического запуска до первого
контрольного вызова. Новый план после нативной проверки должен быть зафиксирован
до начала измерений. Для генерации A/B/C/D выполнить команду без `--prepare-only`
и `--preflight-only`:

```sh
python3 scripts/evaluate_privacy_policy.py \
  --model-dir /absolute/path/to/models \
  --runtime /absolute/path/to/llama-server \
  --output artifacts/privacy-policy-phase2/gemma-new-profile
```

Без дополнительных флагов стенд использует политику v1, все четыре свежих варианта
и профиль из таблицы. При сознательной смене runtime требуется явный
`--expected-runtime-sha256 <sha256>`; это новый профиль, а не молчаливая замена
исторического исполняемого файла. Любое изменение настроек записывается в signature.
Не копировать абсолютные `/tmp`-пути и служебные запускаторы старой сессии.

Проверка документации:

```sh
python3 scripts/check_docs.py
```
