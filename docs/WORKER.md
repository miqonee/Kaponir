# Фоновый анализ документов

[Документация](README.md) · [Команды](COMMANDS.md#worker) · [Discover](DISCOVERY.md)

Worker обрабатывает документы и сохранённые запросы отдельно от прокси. Найденные значения
попадают в зашифрованную подборку; правила появляются только после подтверждения.
Прокси использует быстрые детекторы и правила; Qwen и S1/Choice работают в фоне.
См. [обнаружение, категоризация и обучение](LEARNING.md).

## 1. Минимальный CLI

Обычным `mask`, `restore` и прокси Python не нужен. Для воркера нужен Python 3.12+;
`KAPONIR_WORKER_PYTHON` позволяет указать его исполняемый файл.

```sh
kaponir init
kaponir serve
```

Откройте **LLM и Анализ → Включить воркер**. Сервер запускает один дочерний процесс,
проверяет его доступность и активирует очередь. Модель при этом не скачивается.
Выключение приостанавливает обработку и освобождает модель; очередь и кандидаты остаются.
Состояние включения сохраняется, поэтому включённый воркер возобновляется при следующем запуске сервера.
Процесс управления завершается вместе с сервером, включая остановку по SIGTERM.

Для самостоятельного запуска:

```sh
kaponir worker serve
# Либо только управляющий API, с обработкой, выключенной при первой установке:
kaponir worker serve --idle
```

Обычный явный `serve` начинает с включённой обработки, если ранее не сохранено другое состояние.
Загрузка моделей и создание заданий — отдельные действия. `run` явно выполняет одно задание.

## 2. Worker и UI на одной машине

В обычном `kaponir serve` отдельный `serve.worker_url` для управляемого дочернего процесса не нужен.
Настройки `[worker]` в `KAPONIR_HOME/config.toml`:

```toml
[worker]
listen = "127.0.0.1:8788"
input_root = "inbox"
data_dir = "worker"
model_dir = "models"
threads = 2
```

Относительные пути отсчитываются от `KAPONIR_HOME`. Для управляемого процесса создаётся каталог
входных файлов. В UI показываются готовность, ошибки запуска, состояние модели, очередь и прогресс.
Для уже запущенного отдельного процесса укажите `KAPONIR_WORKER_URL=http://127.0.0.1:8788`.

Текстовым файлам дополнительные Python-пакеты не нужны. Для изображений и PDF:

```sh
python3 -m venv .venv-worker
.venv-worker/bin/python -m pip install -r scripts/requirements-worker.txt
export KAPONIR_WORKER_PYTHON="$PWD/.venv-worker/bin/python"
```

Для OCR изображений/сканов также нужен Tesseract с языками rus/eng. Для PDF с текстовым слоем
используется pypdfium2. Статус API различает наличие OCR и модельного runtime.

## 3. Docker Compose

```sh
cp deploy/compose.env.example .env
# Заполните токен доступа и при необходимости отдельный токен воркера.
mkdir -p documents
docker compose up -d --build
```

Стандартный Compose запускает прокси и управляющий сервис воркера. На новой установке очередь
выключена; **LLM и Анализ → Включить воркер** активирует её без пересборки контейнеров.
Если отдельный токен воркера не задан, используется токен доступа к прокси.

Модели, очередь и Vault находятся в volumes. Входной каталог смонтирован read-only.
Образ воркера содержит Pillow, pypdfium2 и Tesseract с rus/eng; Qwen и llama-server загружаются
отдельно по кнопке. Не удаляйте volumes при обычном обновлении.

Для заранее собранного Linux-бинарника нужной архитектуры:

```sh
cargo build --locked --release -p kaponir-cli
KAPONIR_BUILD=prebuilt docker compose up -d --build
```

Запуск только прокси остаётся доступен через `docker compose up -d kaponir`.

## 4. Worker на другом сервере

На машине воркера запустите `kaponir worker serve` с подходящими `input_root` и `listen`.
Для не-loopback адреса требуется `KAPONIR_WORKER_TOKEN`.

На прокси задайте `KAPONIR_WORKER_URL` и тот же `KAPONIR_WORKER_TOKEN`. На воркере задайте
`KAPONIR_WORKER_API_URL` (адрес прокси) и `KAPONIR_API_TOKEN` для импорта кандидатов и анализа сессий.
Сервер не пытается запускать произвольный процесс на удалённой машине: UI активирует обработку
через управляющий API подготовленного сервиса. У старого сервиса без этой возможности кнопка недоступна.

## Поиск кандидатов моделью

Режимы задания:

- `configured` — общая очередь фонового обучения с настройками обнаружения и категоризации из панели.
- `local` — быстрые детекторы и извлечение текста из файла, без вызова Qwen.
- `qwen` — локальная текстовая модель предлагает значения, затем выполняются детекторы и проверка по источнику.
- `xiaomi` — прежний идентификатор режима, совместимый с `qwen`; новая модель Xiaomi не запускается.

Поддержаны Qwen3-0.6B Q4_K_M (397 MB), Q8_0 (639 MB) и Qwen3.5-0.8B Q4_K_M (533 MB).
Прежние задания с каноническим ID `q5` продолжают использовать Qwen3-0.6B Q8.
Новые задания с ID `qwen3.5-0.8b` используют настоящую Qwen3.5.
Автоустановка llama-server предусмотрена для Linux x64; на других платформах нужен совместимый
runtime, заданный в `[worker] runtime`. Загрузка проверяет размеры и SHA-256.

Модель получает текст фрагментами. Значения проверяются по точным цитатам в оригинале;
само наличие цитаты не считается доказательством конфиденциальности. Пароли/ключи, найденные
в документе, не передаются в дополнительную оценку S1. Отклонение кандидата создаёт отрицательную
обучающую метку, а не KEEP-правило. Веса Qwen от этого не изменяются.

## Анализ сессий: что доступно

В подразделе воркера выберите «Разобрать сессии прокси» или источник `@sessions`.
Используются последние сохранённые завершённые запросы: сессии объединяются по тому же ID,
повторная история внутри них не подаётся как отдельные документы. В режиме `qwen` экспорт
проходит через тот же модельный анализ, что и обычный файл.

`GET /api/v1/ui/sessions/export` выдаёт документы с проверкой доступа и `Cache-Control: no-store`.
Без адреса прокси анализ сессий завершается явной ошибкой. Отдельная кнопка в «Правилах из документов»
выполняет быстрый анализ сохранённых сессий без воркера. Это разовый разбор доступной истории,
а не определение момента окончания живого разговора и не наблюдение за каталогом.

TXT/Markdown/JSON/JSONL-экспорты также можно подать обычным файлом.

## Файлы и управление заданиями

Пути заданий должны находиться внутри `input_root`; абсолютные пути, выход из каталога и symlink
не принимаются. Поддержаны текстовые файлы, изображения и PDF. Ограничения размера, числа файлов
и страниц задаются в `[worker]`. Изменившийся после постановки файл не обрабатывается молча.

Пауза сохраняет прогресс. Выключение воркера приостанавливает активное задание; включение продолжает
именно такую паузу, не снимая паузы, заданные пользователем вручную. Отмена оставляет уже собранные
кандидаты. Повторное включение не создаёт второй процесс и не загружает модель.

API прокси: `GET /api/v1/ui/worker`, `POST .../start`, `POST .../stop`; модели и задания используют
прежние `/models/download`, `/jobs` и `/jobs/{id}/{pause|resume|cancel}`. Статус сообщает `can_manage`,
`enabled`, `online`, `state`, зависимости и очередь. Активация сервиса: `POST /enable`, `POST /disable`.

## Модель и обучение

S1 n-gram обучается командой `kaponir s1 train` по подтверждённым данным. Отключённые правила
не входят в обучение или профиль. Это не обучение весов Qwen и не работа модели в каждом запросе.

## Что можно делать с Xiaomi сейчас

[Xiaomi-OCR-0 оценивалась ранее](XIAOMI_OCR_EVALUATION.md). Это историческое исследование другой
модели. Текущий worker использует Qwen для текстовых кандидатов и Tesseract для OCR;
цифры старой оценки не описывают качество текущего конвейера.

## Конфигурация и обновление

Существующие файлы настроек и очередь сохраняются. На новой установке `--idle` начинает с выключенной
обработки; сохранённое состояние имеет приоритет. Перенос общих настроек описан в
[SETTINGS_TRANSFER.md](SETTINGS_TRANSFER.md); это не резервная копия Vault или очереди.

## Qwen3.5 и ресурсы

Доступна настоящая Qwen3.5-0.8B Q4_K_M из `unsloth/Qwen3.5-0.8B-GGUF`.
Ревизия закреплена, размер 532 517 120 байт, SHA256 проверяется при установке.
Существующие Qwen3-0.6B Q4/Q8 сохранены. Веса не загружаются при включении обработки.

Параллельность фонового обучения — 1–10. На CPU используются одни веса и несколько
слотов llama-server; разные модели сменяются после завершения текущих обращений.
Модель освобождается при отключении и после 30 секунд простоя. Виджет показывает
RSS воркера и модели на Linux. Не следует приравнивать размер GGUF к потреблению ОЗУ.

В изолированном коротком CPU-прогоне Qwen3.5 извлекла «Лунная Слива»; RSS модели
составлял около 922 МиБ при одном слоте. Это проверка запуска, не общий бенчмарк точности
или гарантия памяти для других контекстов и уровней параллельности.
