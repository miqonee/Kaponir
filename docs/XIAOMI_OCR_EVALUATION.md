# Xiaomi-OCR-0 для фонового анализа и настройки Kaponir

[Документация](README.md) · [Актуальное руководство worker](WORKER.md)

> Исследовательский документ. Актуальные команды и ограничения эксплуатации приведены
> в [WORKER.md](WORKER.md); результаты ниже относятся к указанным синтетическим страницам.

Интеграция OCR-worker теперь реализована: [запуск через CLI/UI/Compose](WORKER.md).
Он получает OCR-текст и передаёт его в discover. Режим `--mode xiaomi` также
извлекает кандидатов самой моделью и сверяет их с текстом; правила подтверждает пользователь. Ниже — результаты испытания и исходная оценка.

## Практическая польза

Xiaomi — дополнительный источник кандидатов для базы правил. Её полезно запускать
по каталогу договоров, сканам или сохранённым экспортам диалогов: модель может предложить
значения, которых не заметили локальные распознаватели. После подтверждения точное
правило используется в последующих запросах без повторного запуска Xiaomi.

В текущем worker есть два режима: `local` (локальный поиск, OCR при необходимости)
и `xiaomi` (дополнительный поиск моделью). S1 может оценивать находки; подтверждение
остаётся ручным. Метки можно использовать для отдельного обучения локального S1,
веса Xiaomi при этом не меняются. Автоматической записи/анализа завершившихся сессий нет:
пользователь передаёт экспорт файлом.

## Результаты практических проверок

Проверки выполнены 2026-11-02 на CPU, только на синтетических документах.
Распознавание текста, извлечение полей и определение конфиденциальности — разные задачи.

| Задача | Вариант и вход | Наблюдавшийся результат |
|---|---|---|
| OCR | Q4_K_M, две чистые страницы EN/RU | Прочитаны все 18 контрольных значений, включая публичные. Это не метрика обнаружения секретов. |
| Извлечение полей в JSON | Q5_K_M, те же страницы | По 8/9 полей с правильными ключами и значениями. Общий OCR-результат «18/18» для Q5 в этом прогоне не измерялся. |
| Выбор mask/keep | Q4/Q5, страницы с указанием публичных/закрытых полей | Ошибки структуры и классификации; переход на Q5 их полностью не устранил. |
| Поиск кандидатов в рабочем worker | Q4_K_M, два коротких текстовых документа EN/RU | 3 точных значения против 0 предложений локального discover. Пропущено одно внутреннее название, одна фраза доступа получила тип CUSTOM. |
| Полный сценарий UI | Q4_K_M, каталог этих двух текстов | Задание завершено за 98,4 с при 2 потоках CPU. Кандидат подтверждён в UI; затем название маскировалось целиком. |
| Полный сценарий контейнера | Q4_K_M, один PNG | OCR → поиск → подборка, 78,7 с при лимите 2 CPU / 2560 MB. Найдена фраза доступа, внутреннее название пропущено. |

В модельном поиске точные находки — «Лунная Слива», `tulip-fog-482` и
`туман-482-ирис`; название `Ember Finch` рабочий режим пропустил. Прямой текстовый
ввод Q4 давал переводы и выдуманные строки, поэтому worker отрисовывает текст
страницами. Проверка совпадения с источником отсекает выдуманные значения, но сама
по себе не определяет конфиденциальность или правильность категории.

В первом исследовательском прогоне запросы с изображением занимали 36–71 с,
пик RSS процесса — около 1,45 GiB при 3 потоках CPU. Это измерения конкретных
запросов; времена полного worker включают другие этапы и напрямую с ними не сравниваются.
Один процесс worker убирает анализ из пути запроса прокси, но на общем хосте
продолжает использовать общие CPU/RAM.

Подробные ответы и протоколы сохранены в локальных архивах
`artifacts/xiaomi-ocr-test-2026-11-02/` и `artifacts/xiaomi-candidates-2026-11-02/`.
Они исключены из Git; основные результаты приведены здесь, чтобы документация
оставалась самодостаточной после клонирования. Протокол поиска включает проверку
S1 тестовым провайдером; внешний S1 в этом прогоне не вызывался.

## Что подтверждено источниками

[Xiaomi-OCR-0](https://github.com/xiaomi-research/Xiaomi-OCR-0) — модель
vision-language на 0.8B параметров на базе Qwen3.5-0.8B. Поддерживает:

- разбор страницы в структурированный Markdown, таблицы и формулы;
- Key Information Extraction: извлечение запрошенных полей по JSON-схеме;
- вопросы по тексту/содержимому изображения (VQA).

В [карточке модели](https://huggingface.co/SeerRay-Lab/Xiaomi-OCR-0)
есть пример KIE для чека: дата, продавец, адрес, налоговый идентификатор, суммы.
Это полезный механизм для предложения реквизитов и других значений, но не готовая
классификация всех видов конфиденциальности. OCR/VQA-бенчмарки не измеряют полноту
обнаружения секретов по корпоративной политике.

Лицензия репозитория и карточки весов — Apache-2.0. Для конкретного стороннего
пакета нужно учитывать и его состав/условия.

## Как встроить в настройку

Ниже — схема с возможным расширением KIE. В worker есть OCR и фиксированный запрос
поиска кандидатов (`--mode xiaomi`). Свободные вопросы и пользовательские схемы KIE
ещё не подключены к очереди/UI.
Рабочие сценарии и границы анализа сессий описаны в
[руководстве worker](WORKER.md#что-можно-делать-с-xiaomi-сейчас).

1. Пользователь запускает задание по своим документам.
2. Из текстовых файлов и PDF с текстовым слоем извлекается текст обычным парсером.
   OCR применяется к сканам и изображениям.
3. Xiaomi-OCR-0 выдаёт текст/структуру страницы; при необходимости KIE предлагает
   заданные поля (например, название клиента, номер договора, реквизиты, суммы).
4. Текст проходит существующий discover; KIE-кандидаты проверяются по источнику
   и объединяются с локальными находками. Для выводов, не найденных в распознанном
   тексте, требуется проверка по странице; автоматически правила из них не создавать.
5. Пользователь видит значения, страницу/пример и подтверждает правила/метки.
   Затем OCR-процесс может быть выгружен, а обычный прокси работает с сохранёнными правилами.

В [демо](https://github.com/xiaomi-research/Xiaomi-OCR-0/blob/main/demo/README.md)
PDF поддерживает разбор страниц; KIE/VQA работают с изображениями. Для KIE по PDF
нужно использовать изображения отдельных страниц. Для обычного page-mode
дополнительный PaddleX/PP-DocLayoutV3 не требуется; region-mode требует отдельной
модели разметки и зависимостей.

## Ресурсы и размещение

[Ollama BF16](https://github.com/xiaomi-research/Xiaomi-OCR-0/blob/main/OLLAMA.md)
обозначен авторами как экспериментальный. Упоминавшийся в исходной оценке community-пакет
с vision projector занимал около **1.8 GB на диске**. Встроенный worker сейчас загружает
другие фиксированные Q4/Q5-варианты: около **737/785 MB** вместе с визуальным модулем;
их фактические CPU-измерения приведены выше. Размер пакета — не обещание требуемой RAM/VRAM:
память и скорость также зависят от разрешения страницы, контекста, runtime и
числа параллельных задач. Требования для новых типов документов нужно измерять отдельно.

Есть варианты vLLM/SGLang и Ollama. Документация описывает проверки на Apple Silicon
и NVIDIA RTX 4090; случай с выгрузкой слоёв на CPU подтверждает работоспособность,
а не скорость. Community-квантизации доступны, но заявленные исходные бенчмарки
не доказывают их качество.

Для Kaponir предпочтителен отдельный worker с очередью, ограничением числа страниц,
одной задачей одновременно и возможностью выключения после обработки. Worker может
работать на компьютере пользователя или другом сервере. Если он находится на том же
сервере, что прокси, общие CPU/RAM/GPU всё равно конкурируют: нужны ограничения
ресурсов или запуск вне пика. В основной запрос агента этот OCR не включать.

## Что ещё проверить на своих документах

- Русские договоры, фотографии, повёрнутые и зашумлённые сканы, таблицы и мелкие реквизиты.
- Полноту и точность кандидатов, совпадение извлечённых значений с источником.
- Время и пиковую память на целевом оборудовании; качество выбранной квантизации.
- Многостраничные PDF и большие каталоги. Чистые синтетические страницы из первого
  практического прогона не покрывают эти условия.

Вывод: подходящий кандидат для дополнительного способа автоматической настройки
через OCR и извлечение полей. Обещать извлечение всех конфиденциальных сведений
только этой моделью оснований пока нет.
