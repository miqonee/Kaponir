# Kaponir — обратимый анонимайзер: архитектура и решения

[Документация](README.md) · [Возможности](../README.ru.md#что-умеет-kaponir) ·
[Безопасность](SECURITY.md) · [Участие](../CONTRIBUTING.md)

Документ фиксирует решения, принятые при обсуждении исходной спецификации.
Если код расходится с документом — правится одно из двух, расхождение не живёт долго.

## 0. Принципы

1. **Ядро — чистая библиотека.** Без сети, диска и знания языков. На вход текст + правила + vault,
   на выход замены и журнал решений. Всё остальное — адаптеры.
2. **Deny-by-default в структурных слотах.** Неизвестный сегмент пути, поддомен, часть имени пода
   маскируется. Сохраняется только то, что есть в allowlist (тех-словарь, словари языковых пакетов,
   публичные домены).
3. **Детерминированный слой отвечает за безопасность, обучение — за удобство.** Без S1 система
   полностью рабочая; S1 никогда не ослабляет жёсткие правила.
4. **Спорное по умолчанию маскируется.** Ошибка S1 сохраняет локальные решения до его вызова;
   дальнейшее поведение задаёт политика `uncertain` (по умолчанию `mask`, настраивается и `keep`).
   Неизвестный формат не освобождает текст от обработки обычными детекторами. Сбой S1 не
   создаёт кандидатов для фрагментов, которые детекторы не нашли.
5. **Ничего языкового и регионального в ядре.** Языки и юрисдикции — пакеты.

## 1. Режимы и интеграция

| Способ | Как | Для чего |
|---|---|---|
| Цепочка прокси | `клиент → kaponir → 9router → провайдер` или наоборот | Интеграция без изменения кода |
| Sidecar REST | `/api/v1/anonymize`, `/api/v1/deanonymize`, потоковое восстановление по сессии | Шлюзы, управляющие потоком сами |
| Библиотека | Rust-крейт; позже C ABI / napi-rs / PyO3 / WASM | Встраивание в процесс |
| CLI / Web UI | `kaponir mask`, `kaponir restore`, `kaponir review`, `kaponir ui` | Ручная работа, пайпы, CI |

Сквозная сущность — **сессия** (`X-Kaponir-Session`): связывает маскирование запроса и восстановление
ответа, даже если их выполняют разные компоненты.

## 2. Формат токенов

| Контекст | Форма | Пример |
|---|---|---|
| Проза, код, значения конфигов, пути | `ANON_<KIND>_<N>` | `/home/ANON_USER_1/ANON_PROJ_1/k8s/values.yaml` |
| DNS-метки, хостнеймы, поды | `anon-<kind>-<n>` | `harbor.anon-sub-1.anon-dom-2.ru` |
| HMAC-режим | `ANON_<KIND>_h<hex>` / `anon-<kind>-h<hex>` | `anon-svc-h8f2a1c` |

- `KIND` — `[A-Z][A-Z0-9]*`, одно слово (`USER`, `PROJ`, `DOM`, `SUB`, `SVC`, `SECRET`, `IP`…).
- Префикс настраивается (`token.prefix`), по умолчанию `ANON`.
- Только ASCII, без `$ { } < >`: токен не раскрывается в shell/Helm/Jinja и не требует кавычек
  в YAML/JSON, поэтому подставляется в любую позицию без экранирования.
- **Граница справа.** Если сразу после маскируемого фрагмента идёт цифра, она поглощается
  фрагментом (иначе `ANON_SVC_1` + `2` неотличимо от `ANON_SVC_12`). Восстановление точное,
  так как цифры входят в оригинал.
- **Литералы.** Если во входе уже есть строка вида токена, её номер резервируется в vault
  и никогда не выдаётся — при восстановлении она останется как есть.
- **Стабильность.** Один оригинал (по каноническому ключу) всегда получает один номер.
  Это сохраняет prompt caching у провайдера.
- В локальном vault счётчик номеров общий для kind (не по scope), поэтому токены разных
  scope не пересекаются. Для серверного режима — пространство имён в номере (решим на этапе 3).

### HMAC-режим

`id = hex(HMAC_SHA256(hmac_secret, kind ‖ canonical))[..6]`; при коллизии в vault длина растёт до 8–16.
`hmac_secret` задаётся отдельно, чтобы псевдонимы совпадали между машинами команды.
Режим `--irreversible`: HMAC без записи в vault — восстановление невозможно, vault ничего не хранит.

### Суррогаты IP (format-preserving)

- IPv4 → **240.0.0.0/4** (класс E, не маршрутизируется). Первые 24 бита оригинала проходят
  prefix-preserving перестановку (схема Crypto-PAn на HMAC), берутся 20 бит, хост-октет сохраняется:
  общий префикс у оригиналов ⇒ общий префикс у суррогатов.
- Суррогат хранится в vault; при коллизии используется обычный токен `ANON_IP_N`.
- Служебные адреса (`127.0.0.0/8`, `0.0.0.0`, маски `255.*`, broadcast) не маскируются.
- IPv6 на этапе 1 — токены; суррогаты в `2001:db8::/32` позже.

## 3. Восстановление

- Поиск без учёта регистра и разделителя: `(?i)PREFIX(\\?[_-])KIND(\\?[_-])(N|h<hex>)`.
  Находит `anon_user_1`, `ANON-USER-1`, `ANON\_USER\_1` (markdown).
- Обёртки `${…}`, `$…` вокруг токена снимаются.
- Буквенный хвост после токена (`ANON_PERSON_1у`, `ANON_PERSON_1's`) отдаётся языковому пакету:
  RU склоняет оригинал, EN оставляет суффикс, по умолчанию суффикс сохраняется.
- Похожие на токен строки без записи в vault попадают в отчёт (`unknown_tokens`).
- Права проверяются по scope записи (см. §8).

### Потоковое восстановление (SSE)

Автомат придерживает только хвост буфера, который может оказаться началом токена или суррогата
(не длиннее `max_hold`). Всё остальное уходит клиенту сразу.
Два режима вывода: `Text` и `JsonString` (для `input_json_delta` в tool_use: подставляемое значение
экранируется по правилам JSON — иначе Windows-путь или кавычка сломают аргументы инструмента).

## 4. Конвейер

```text
текст ─► [BLAKE3 кэш блоков] ─► Recognizers ─► ContextEnhancer ─► Scorer(log-odds [+S1]) ─►
        Decision(MASK/KEEP/UNCERTAIN) ─► ConflictResolver ─► TokenAllocator(Vault) ─► текст + журнал
```

### Recognizer

```rust
pub trait Recognizer: Send + Sync {
    fn id(&self) -> &str;
    fn analyze(&self, input: &Input, out: &mut Vec<Candidate>);
}
```

`Candidate` = диапазон байтов + kind + категория + канонический ключ + полярность (`Mask`/`Keep`)
+ происхождение (встроенный детектор или правило со scope) + свидетельства (log-odds) + `hard`
(учётные данные и значения с валидной контрольной суммой) + форма токена (`Snake`/`Dns`).

### Оценка: log-odds

```text
logit(p) = prior(детектор) + Σ context_boost + validator_bonus + w_s1 · logit(p_c)
```

Решение — по порогам категории: `p ≥ τ_mask` → MASK, `p ≤ τ_keep` → KEEP, иначе UNCERTAIN.
UNCERTAIN применяется по политике (по умолчанию MASK) и пишется в журнал решений.
Без S1 его слагаемое равно нулю — формула и пороги те же.
`p_c` — оценка S1 после преобразования Платта. Для HTTP по умолчанию это практически исходная
оценка (`a = 1`, `b = 0`), а не вероятность с подтверждённой точностью. S1 применяется только
к отобранным спорным кандидатам; переход в KEEP дополнительно ограничен `keep_below`.
Точные условия и порядок — в [S1.md](S1.md#как-оценка-влияет-на-решение).

### Разрешение пересечений

Порядок старшинства:
1. уровень происхождения: `Global enforced` > `Global` > `Team` > `Personal` > встроенный детектор;
2. итоговая вероятность;
3. длина совпадения.

`Keep`-кандидат (allowlist, «никогда не маскировать») не может перекрыть `hard`-маску, если
сам не является `Global enforced`.

### Конфиги (AST-aware без пересериализации)

Парсеры находят позиции, замены точечно применяются к исходным байтам — комментарии, отступы,
кавычки, якоря сохраняются. Универсальный сканер пар ключ-значение понимает YAML (включая
блочные скаляры `|`/`>`), JSON, TOML, `.env`, INI и флаги CLI (`--password x`).
1. Проход по ключам: ключ под маской (`password`, `secret`, `token`, `dsn`, `private_key`,
   `bucket`, `endpoint`…) ⇒ значение маскируется целиком, даже если похоже на обычное слово.
2. Проход по значениям: весь текст проверяется остальными детекторами.

### Составные маски (Composite DSL)

Шаблон компилируется в регулярное выражение; `{KIND}` в верхнем регистре — чувствительный слот,
в нижнем — сохраняемый класс:

```toml
[[mask]]
template = "{env:prod|stage|dev}-{SVC}-{hash}"
```

Встроенные классы: `{hash}`, `{num}`, `{word}`, `{any}`; `{name:a|b|c}` — перечисление.

Встроенный разбор идентификаторов (пути, URL, поддомены, поды) режет сегмент по `-_.`,
части из словарей и хеш-подобные части (`7d9f8b`, `x2v`) сохраняются, подряд идущие неизвестные
части сливаются в один слот: `prod-billing-auth-7d9f8b-x2v` → `prod-ANON_SVC_1-auth-7d9f8b-x2v`.

## 5. Пакеты

| Тип | Содержит | Примеры |
|---|---|---|
| `lang-*` | Имена, шаблоны ФИО, морфология, слова контекста, словари коллизий, общие слова | `lang-ru`, `lang-en` |
| `region-*` | Документы и реквизиты юрисдикции, форматы телефонов и адресов | `region-ru` (ИНН, СНИЛС, ОГРН, БИК/счёт) |
| `domain-*` | Предметные словари | `tech` (k8s, helm, nginx…) |
| `common` | Универсальные валидаторы | Луна, IBAN, энтропия |

**Пакеты-данные** (без кода): `pack.toml` + текстовые списки, загружаются из каталога или
встраиваются. **Пакеты-код**: Rust-крейт, реализующий `LanguagePack`/`Recognizer`, подключается
фичей Cargo; позже — WASM-плагины.

```text
packs/lang-xx/
├── pack.toml            # id, version, api_version, kind, scripts, license
├── words.txt            # общие слова (allowlist для слотов)
├── context.toml         # kind -> слова-усилители
├── names/given.txt      # имена (этап 2)
├── names/patterns.toml  # суффиксы фамилий/отчеств, шаблоны ФИО (этап 2)
├── collisions.txt       # фамилии, совпадающие со словами (этап 2)
└── tests/corpus.jsonl   # размеченные примеры для `kaponir pack test`
```

```rust
pub trait LanguagePack: Send + Sync {
    fn id(&self) -> &str;
    fn scripts(&self) -> &[Script];
    fn lexicon(&self) -> &Lexicon;
    fn canonicalize(&self, kind: &str, surface: &str) -> Option<String> { None }
    fn restore_form(&self, original: &str, suffix: &str) -> Option<String> { None }
    fn recognizers(&self) -> Vec<Box<dyn Recognizer>> { vec![] }
}
```

Детектор имён — общий в ядре; пакет поставляет типы признаков (известное имя, отчество,
обращение, инициалы, шаблон фамилии, коллизия, контекст) с весами. Контекст строчной словоформы
читается и после JSON escape-последовательности (`\\n`, `\\r`, `\\t`), а левая граница окна
не обрезает слово. Канонизация: RU — лемма и нормальный порядок, EN — регистр/`'s`/порядок.
У строчной и заглавной форм имени разные canonical-ключи: склонения одного регистра делят токен,
но исходный регистр восстанавливается точно. `lang-ru` даёт схемы транслитерации,
связь `Голошанов ↔ Goloshanov` — предложение, а не автослияние. Язык определяется по сегментам
(письменность по Unicode → набор пакетов). Лицензия данных — поле `license` пакета; полный
fst-словарь OpenCorpora — опциональная фича `ru-morph-full`.

## 6. Обучение без ML и с S1

**Журнал решений** пишется с первого дня: значение (зашифровано), форма, kind, p, причины, контекст.
Web UI разбора и `kaponir review` показывают записи с группировкой по форме и предлагают:
«всегда маскировать как KIND», «никогда не маскировать», «маска по шаблону», выбор scope.
Решение сразу становится правилом. Это интерфейс разбора, а не операционный дашборд трафика прокси.

Для холодного старта `kaponir discover` и `kaponir init --learn <файлы>` локально предлагают
ещё не замаскированные кандидаты встроенных детекторов и суммы с валютой. Предпросмотр не вызывает
S1, не пишет в vault или журнал и не меняет правила. Сохраняются только явно выбранные id как
точные MASK-правила; автоматических KEEP-правил и автоматического снятия масок нет. Во вкладке
Web UI «Настройка» сервер повторно анализирует документы при применении и не доверяет клиентскому
отчёту. Это подтверждаемая первичная настройка, а не автоматически полный корпоративный профиль.
Локальный `ngram` обучается только на подтверждённых значениях журнала и точных правилах;
слабая разметка детекторов не принимается как подтверждение.

### S1 — подключаемый провайдер вероятностей

Единая спецификация текущего поведения: [S1.md](S1.md). Контракт ядра:

```rust
pub trait S1Provider: Send + Sync {
    fn id(&self) -> &str;
    fn max_disclosure(&self) -> Disclosure; // L0 признаки / L1 строка / L2 + очищенный контекст
    fn score(&self, batch: &[CandidateView]) -> Result<Vec<f32>, S1Error>;
    fn score_with_profile(
        &self,
        batch: &[CandidateView],
        profile: &[ProfileValue],
    ) -> Result<Vec<f32>, S1Error> { self.score(batch) }
}
```

S1 классифицирует уже найденные спорные кандидаты встроенных детекторов, не добавляя новые
сущности. `hard`, кандидаты явных правил и значения под применимым KEEP-правилом на оценку
не передаются. Батч формируется на один вызов `Engine::mask`, а не на весь запрос прокси.
Ошибка оценки отменяет весь батч и сохраняет исходные локальные решения; далее действует политика.

L0 передаёт метаданные и признаки; L1 добавляет исходную строку, L2 — окно `[s1] context_bytes`
(по умолчанию 60 байт UTF-8 с каждой стороны, 0–4096). Соседние найденные кандидаты маскируются.
На L2 отдельно передаётся профиль из уникальных точных MASK-правил, если у батча есть реальный
контекст; KEEP, regex и шаблоны исключены. Необнаруженные данные могут остаться в контексте;
L1/L2 раскрывают сам кандидат внешнему сервису, включая теневой режим. Значения категории
credential и пересекающие их кандидаты ограничены L0. L0 не является шифрованием.

В теневом режиме оценка пишется в объяснение с нулевым весом, в активном участвует в log-odds.
Для снятия маски нужны и итоговый KEEP по порогам категории, и `p_c ≤ keep_below`.
Преобразование Платта поддерживается; для HTTP по умолчанию `a=1, b=0`, автоматической подгонки
калибровки нет. Уверенность внешнего провайдера требует независимой проверки.

Реализованы локальный `ngram` и HTTP с протоколами `probabilities` / `systemone`.
`ngram` обучается на подтверждённых уникальных значениях, исключая конфликтующие метки.
`train`, `status`, `rollback` работают с локальной моделью; откат внешнего сервиса не реализован.
Калибровка `ngram` подбирается на k-fold-предсказаниях; итоговые метрики на тех же метках —
диагностика, не независимая оценка. Обучение не меняет выбранный провайдер.
Отдельного согласования ослабляющих Team-изменений с ролями сейчас нет.

HTTP ограничивает очередь, общий бюджет ожидания и размер ответа (1 MiB), не выполняет редиректы
или автоматические повторные попытки. Проверяются полный батч и диапазон вероятностей;
для SystemOne дополнительно — ключи `candidate_N` и тип `noul`. Полный формат запроса,
ограничения раскрытия, настройки и объяснения приведены в [S1.md](S1.md).

По умолчанию S1 выключен. Работающий сервер применяет новую модель/настройки при перезапуске
или пересборке движка при перезагрузке правил. `pack test` работает без S1. Подтверждённый профиль
и настраиваемый байтовый контекст L2 реализованы; обзор трафика, JSON/Prometheus и обезличенные
события сбоев S1 работают в текущей версии. Более широкое обнаружение новых сущностей,
семантический контекст, независимая проверка калибровки и долговременное хранение истории
остаются задачами развития.

## 7. Хранилище (vault)

SQLite, один файл. Значения шифруются ChaCha20-Poly1305, поиск — по слепому индексу
`HMAC(blind_key, scope ‖ kind ‖ canonical)`. Ключи выводятся из мастер-ключа через BLAKE3
`derive_key`. Мастер-ключ: `KAPONIR_VAULT_KEY` или файл ключа с правами `0600`
(связка ключей ОС — позже).

Таблицы: `entries` (scope, owner, kind, n, hmac_id, blind, ciphertext), `counters`, `reserved`
(литералы), `surrogates`, `journal`, `rules` (решения из review). Отдельные структуры vault
хранят сессионную память, зашифрованную подборку discover, обучающие метки, настройки и реестр
подключений. Актуальные правила резервного копирования — в [SECURITY.md](SECURITY.md).

## 8. Модель угроз и RBAC

- Защищаемся от: внешнего LLM-провайдера, сторонних сервисов, чат-логов и трекеров.
- Не обещаем защиту от администратора собственного сервера: в серверном режиме сервер доверенный.
- По умолчанию локальный режим, vault на машине пользователя.
- Team/Global — прежде всего **общие правила** и приоритеты, а не отдельные учётные записи
  или криптографическая граница между пользователями одного сервера. Personal учитывает owner
  при доступе к записям, но всё пространство защищено общим мастер-ключом vault.
- Журнал решений содержит секреты: шифруется, имеет TTL; серверный режим с отдельными ролями
  и разграничением владельцев не реализован.

## 9. Прокси для агентов (этап 2, `kaponir-proxy`, `kaponir serve`)

Эндпоинты: `POST /v1/messages` (+ `/count_tokens`), `POST /v1/chat/completions`, `GET /v1/models`
(как есть), sidecar `POST /api/v1/anonymize`, `/api/v1/deanonymize`, `/api/v1/deanonymize/stream`.
Цепочка с 9router — через `anthropic_upstream` / `openai_upstream`.

- **Запрос.** Маскируются system, текстовые блоки, `tool_result`, `tool_use.input` и
  `tool_calls[].function.arguments` (по листьям разобранного JSON, а не сырым текстом), текстовые
  документы. Схемы инструментов — нет. Блоки `thinking` не трогаются ни в запросе, ни в ответе:
  провайдер проверяет их подпись; модель видела только токены, так что оригиналов там нет.
- **Сбой маскирования ⇒ запрос не отправляется** (500). Сбой восстановления ⇒ клиент получает токены.
- **Ответ.** Свой `StreamRestorer` на блок: `text_delta` — `Escape::None`, `input_json_delta` и
  `arguments` — `Escape::Json`. Хвост, похожий на начало токена, придерживается и дописывается
  дельтой перед `content_block_stop` / в чанк с `finish_reason` / перед `[DONE]`.
- **Сессия**: `X-Kaponir-Session`, иначе BLAKE3 первого сообщения разговора. Явные сессии общие для
  прокси и REST.
- **Память сессии** (`Known`): значения, замаскированные или восстановленные в разговоре, маскируются
  тем же токеном в следующих запросах, даже если детекторы их не находят (оригинал из восстановленного
  ответа иначе ушёл бы провайдеру из истории). Хранится в vault зашифрованной, TTL — как у журнала.
- **Кэш**: BLAKE3 исходного блока → замаскированный. История не маскируется заново, префикс запроса
  байт-в-байт стабилен между ходами (prompt caching). JSON пересобирается с сохранением порядка ключей.
- Подсказка о плейсхолдерах дописывается в **конец** system (начало system prompt клиента не меняется)
  и не содержит конкретных токенов.
- Доступ: по умолчанию `127.0.0.1`; на другом адресе — только с `api_token`
  (`Authorization: Bearer` для REST, `x-kaponir-token` для прокси).
- Рассуждения OpenAI-совместимых провайдеров (`reasoning_content`, `reasoning`) не подписаны —
  маскируются и восстанавливаются как текст (в потоке — свой восстановитель на поле).
- Значение из памяти сессии внутри более длинной маски её не дробит (`m.ivanov@corp.ru` — один
  токен EMAIL), но применяется, если длинная маска проиграла другому кандидату.
- Не сделано: OpenAI Responses API. Имена RU/EN в прозе распознаются общим детектором;
  `lang-ru` добавляет склонение и восстановление словоформ, `lang-en` — словари и шаблоны имён.
- Защита от DNS rebinding: без `api_token` принимаются только запросы с loopback-именем в `Host`
  (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`), иначе 403 — для прокси, REST и UI.

## 9a. Web UI (этап 3, `kaponir ui`, `/ui/` на том же сервере)

Страница без сборки фронтенда (HTML/JS/CSS вшиты `include_str!`), строгий CSP (`script-src 'self'`),
пользовательские значения попадают в DOM только как текст. Вкладки:

- **Маскирование** — split view: исходник (textarea поверх подложки с подсветкой по контурам) и
  результат с токенами. Каждое изменение — предпросмотр (`/api/v1/ui/mask`, транзакция vault
  откатывается, журнал не пишется); «Сохранить и копировать» записывает токены и спорные решения.
  Click-to-mask: выделение в исходнике или в результате → тип + «только в этом тексте» (значение
  уходит в запрос как `Known`, правило не создаётся) / «всегда маскировать» в личные или командные
  правила / «никогда не маскировать». Клик по токену — оригинал, источник, p и «не маскировать».
  Таблица всех кандидатов с вердиктами и свидетельствами.
- **Восстановление** — текст с токенами → оригиналы, неизвестные токены и токены без прав отдельно.
- **Разбор** — журнал спорных решений группами (тип + форма) или списком; «маскировать всегда»,
  «никогда не маскировать», «закрыть», маска по шаблону. Решения → правила выбранного контура.
- **Настройка** — файлы или вставленные документы → локальный предпросмотр без S1 и записи →
  явный выбор предложений → точные MASK-правила выбранного контура. При применении сервер заново
  анализирует документы и проверяет id, не принимая клиентские значения правил.
- **Правила** — контуры Global/Team/Personal: корпоративные домены, правила (добавить/удалить),
  загруженные пакеты.

Правила хранит приложение (`trait Control` в `kaponir-proxy`, реализация `HomeControl` — файлы
`KAPONIR_HOME/rules/*.toml`, правка точечная, комментарии сохраняются). После изменения движок
пересобирается и подменяется (`State::replace_engine`) без перезапуска; кэши замаскированных блоков
сессий сбрасываются, чтобы история разговоров маскировалась по новым правилам.

API: `GET /api/v1/ui/info`, `POST /api/v1/ui/mask {text, format, scope, strategy, adhoc[], commit}`,
`POST /api/v1/ui/restore`, `GET /api/v1/journal?status=`, `POST /api/v1/journal/decide
{action: mask|keep|dismiss, ids | shape+of_kind, kind, scope}`, `POST /api/v1/journal/template`,
`GET|POST /api/v1/rules`, `DELETE /api/v1/rules/{scope}/{index}`, `PUT /api/v1/rules/{scope}/domains`,
`POST /api/v1/ui/discover {documents}`, `POST /api/v1/ui/discover/apply {documents, ids, scope}`.
Доступ — как у sidecar REST (`Authorization: Bearer`, если задан `api_token`; UI спрашивает токен
и держит его в `sessionStorage`).

Решения ядра, сделанные на этом этапе:
- Кандидат, покрытый «никогда не маскировать» (правило не младше по контуру; жёсткие маски — только
  enforced), получает вердикт KEEP ещё до разрешения пересечений: он не маскируется, не считается
  спорным и не возвращается в журнал (свидетельство `rule-keep`).
- Форма токена значения из памяти сессии выбирается по месту вхождения: внутри хостнейма или имени
  пода (`-`/`.` рядом) — `anon-x-1`, иначе как при первом маскировании.

## 10. Производительность

Воспроизводимый бенчмарк: `cargo run --release -p kaponir-cli --example benchmark -- 10`.
Он измеряет маскирование и восстановление на 10 КБ, 100 КБ, 1 МБ и обработку потоковых
фрагментов; S1 выключен, vault в памяти. Методика и ограничения — в [OPERATIONS.md](OPERATIONS.md).
Цель малой задержки требует профилирования; бенчмарк не является production SLA.

## 11. Этапы

1. **Ядро + CLI + локальный vault**: токены, детекторы (секреты, IP, email, домены/URL, пути,
   конфиги, составные маски, словари), валидаторы `common` и `region-ru`, журнал решений,
   `kaponir review`, трейты `LanguagePack`/`S1Provider`.
2. **Прокси + sidecar REST**: Anthropic/OpenAI, потоковое восстановление с tool_use.
3. **Web UI**: split view, click-to-mask, интерфейс разбора, правила контуров (сделано). Операционный
   дашборд «Мониторинг», JSON/Prometheus и обезличенные события сбоев S1 реализованы. Серверный
   режим Team/Global с ролями и общим vault — отдельно, после этапа 4.
4. **Языковые пакеты с именами и морфологией (RU/EN), `kaponir discover`, S1-провайдеры.**
   Реализованы распознавание имён RU/EN, русская морфология, исправления строчных фамилий и границы
   JSON, локальный и HTTP S1, обучение/состояние/откат, `discover` / `init --learn` в CLI и Web,
   настраиваемый L2-контекст и подтверждённый профиль только для L2. Независимая проверка порогов,
   расширение языковых корпусов и более широкое обнаружение сущностей остаются направлениями развития.
   Семантические испытания L0/L1/L2 и их ограничения — в [S1.md](S1.md#что-подтверждено-испытаниями).

## 12. Направления развития

- OpenAI Responses API и дополнительные форматы поставщиков.
- Отдельные пользователи, роли и общий многосерверный vault.
- Более широкое обнаружение сущностей и семантический контекст L2.
- Независимая оценка качества и калибровки на новых корпусах.
- Долговременное хранение обезличенной истории и нагрузочные испытания прокси.
- Проверка OCR на фотографиях, поворотах, шуме, таблицах и разнообразных PDF.
