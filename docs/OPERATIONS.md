## Полнота маскирования

`cargo test -p kaponir-cli --test corporate` воспроизводит локальную часть повторного
аудита на 64 документах из `tests/fixtures/corporate-corpus`.
В тесте используются исходники, разметка и три ранее подтверждённых бизнес-правила.
`discover` предлагает название проекта и 64 суммы с валютой; тест явно выбирает их
согласно политике синтетической компании. Затем проверяются отсутствие всех 1344
размеченных значений (8808 вхождений), сохранность публичных терминов и побайтное
восстановление каждого документа. Сохранённые исторические отчёты не изменяются.

Это регрессия известного корпуса, а не независимое измерение полноты на любых данных.
Суммы без валюты и произвольные названия в свободной прозе требуют дополнительных
правил или детекторов. Отдельный тест использует новые названия, суммы, публичный nginx,
версии и счётчики, чтобы проверять переносимость предложения правил и ложные совпадения.
Предложения не становятся правилами без выбора пользователя. Метки «Проект» / `Project`
поддерживают однословные названия с дефисами и подчёркиваниями.

## Наблюдаемость

Главный экран **Обзор** показывает только трафик API-прокси и обновляется каждые 10 секунд
в активной вкладке. Семантика `traffic`, события и мастер настройки — в
[CONTROL_PANEL.md](CONTROL_PANEL.md). Технические счётчики доступны через
**Настройки → Диагностика**, при открытии и по кнопке. Доступны:

- `GET /api/v1/metrics` — JSON и последние 64 обезличенных события сбоев S1;
- `GET /metrics` — счётчики и гистограммы Prometheus;
- stderr процесса `serve` — JSON-строки `event=kaponir_s1_failure` с временем и кодом.

Оба endpoint требуют `Authorization: Bearer`, если настроен `api_token`, и защищены
проверкой Host. Ответы имеют `Cache-Control: no-store`. Метрики не содержат текстов,
значений, токенов, имён сессий, адресов провайдера или его исходных сообщений об ошибках.
Метки гистограмм фиксированы; число рядов не растёт от пользовательских значений.

Семантика счётчиков:

- `mask_calls_total` и `replacements_total` учитывают операции движка, включая Web UI
  предпросмотр и операции, откатившиеся позднее на уровне транзакции. Повтор истории,
  взятый из кэша сессии, повторно не учитывается. Анализ `discover` исключён.
- `restore_calls_total` считает обработанные фрагменты, поэтому один поток может дать
  несколько вызовов. Отдельно считаются восстановленные, неизвестные и недоступные токены.
- `s1_calls_total` — число непустых батчей, `s1_candidates_total` — число кандидатов в них.
  Ошибки и невалидные вероятности увеличивают `s1_errors_total`, локальная политика сохраняется.
- `http_calls_total` учитывает `/v1/*` и `/api/v1/*`, кроме самой выдачи метрик. Ошибками
  считаются HTTP 4xx/5xx. Время — до заголовков ответа, **не** длительность SSE-потока.
  Сбой чтения тела SSE после HTTP 200 учитывается отдельно в `stream_errors_total`.
- Счётчики сохраняются при перезагрузке правил и сбрасываются при перезапуске процесса.
  Гистограмма одного вида операции согласована; общий снимок разных счётчиков может
  отражать соседние моменты времени при конкурентной работе.

Долговременную историю хранит сборщик Prometheus и журнал службы (например, journald).
Само приложение хранит только ограниченную историю в памяти. Настройте хранение stderr
и оповещения на рост `s1_errors_total`, `unknown_tokens_total`, `denied_tokens_total`,
`http_errors_total` и `stream_errors_total` с учётом обычной нагрузки.

Пример Prometheus (секрет хранится в отдельном файле, недоступном другим пользователям):

```yaml
scrape_configs:
  - job_name: kaponir
    scrape_interval: 15s
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/kaponir-token
    static_configs:
      - targets: ['127.0.0.1:8787']
```

## Производительность

```bash
cargo run --locked --release -p kaponir-cli --example benchmark -- 10 > benchmark.json
```

10 КБ, 100 КБ и 1 МБ, один прогрев и указанное число измерений на размер.
Отдельные p50/p95 маскирования, восстановления и обработки потокового фрагмента 256 байт.
Каждый проход проверяет восстановление. Корпус ASCII, повторяющиеся пути и секреты,
S1 выключен, vault в памяти; диск, SQLite, сеть, конкуренция и задержка модели не измеряются.
Это исходная точка для профилирования, а не SLA и не обещание задержки production-прокси.
Прогон 31 октября и сравнение до/после оптимизации сохранены в локальном архиве
`artifacts/quality-2026-10-31/`, исключённом из Git.
Для сравнения сохраняйте rustc, ОС, CPU, число повторов и загрузку машины.

## Независимая оценка S1

`scripts/evaluate_s1.py` принимает два JSONL-набора с уже полученными оценками провайдера:

```json
{"id":"doc17-candidate2","group":"source-document17","label":true,"probability":0.9,"local_probability":0.5,"category":"infra"}
```

`label=true` означает конфиденциальный кандидат. В набор включаются только встроенные
спорные кандидаты, которые действительно допускаются к S1. `local_probability` — оценка
после локальных свидетельств до S1. Файлы не содержат исходных значений. `group` объединяет
документ, его варианты и связанные примеры; одна группа не должна попадать в оба набора.
Дубликаты id, пересечение групп, неизвестные категории и невалидные числа отклоняются.

```bash
python3 scripts/evaluate_s1.py --calibration calibration.jsonl \
  --evaluation independent.jsonl --output evaluation-report.json
```

На первом наборе выбираются положительный наклон и смещение калибровки ограниченным
перебором по log loss; порог `keep_below` выбирается без раскрытий приватных кандидатов
на этом наборе. На втором наборе параметры фиксированы. Отчёт включает раскрытия приватного,
снятые публичные маски, Brier score, log loss, исходную калибровку для сравнения и SHA-256 входов.
Нулевые ошибки не означают нулевой риск: указан верхний предел Wilson 95% на уровне кандидатов.
При зависимых примерах его нельзя интерпретировать как гарантию по независимым документам.

Оценка воспроизводит стандартные пороги категорий, `weight=1`, `uncertain=mask` и дополнительный
барьер `keep_below`. При нестандартной политике она неприменима без адаптации. Результат не
меняет config и не включает активный S1. Наличие раздельных файлов ещё не доказывает
независимость источников; разметку и происхождение проверяет владелец корпуса. Старые
синтетические аудиты нельзя использовать одновременно для настройки и независимой оценки.

## CI, установка и обновление

`.github/workflows/ci.yml` проверяет fmt, Clippy, тесты Rust и Python, release-сборку,
а также упаковку и запуск бинарника из архива. Linux выполняет все проверки; macOS —
тесты, сборку и проверку архива. Удалённые задания запускаются только после размещения
проекта в GitHub. Локальное прохождение проверок не доказывает прохождение macOS CI.

```bash
cargo build --locked --release -p kaponir-cli
python3 scripts/release_check.py target/release/kaponir --output dist
```

Архив содержит бинарник, английский и русский README, CONTRIBUTING, лицензию, актуальные
руководства и пример конфигурации. Журнал работ остаётся в исходном репозитории; объёмные
исторические отчёты хранятся в локальном `artifacts/`, исключённом из Git и release-архива. Скрипт запускает именно
распакованный бинарник, проверяет локальные ссылки и якоря документации архива, `init`,
маскирование, восстановление и сохранность ключей при повторном `init`. Создаёт SHA-256 и
`release-check.json`; существующий архив не перезаписывает.
Зависимости Python не нужны, требуется Python 3.12+ для безопасного распаковывания.
Публикация релиза этим процессом не выполняется.

### Контрольный список перед публикацией репозитория

1. Убедиться, что в корне есть `README.md`, `LICENSE`, `CONTRIBUTING.md`, актуальные `docs/`
   и `.github/workflows/ci.yml`.
2. Проверить `git status --short`: в публикацию не должны попасть `.env`, `vault.db*`,
   `vault.key`, `token.key`, GGUF-веса, реальные документы или экспорт с секретами.
   Правила `.gitignore` уменьшают риск, но не заменяют просмотр состава коммита.
3. Проверить все ранее опубликованные коммиты, если каталог уже был Git-репозиторием:
   удаления секрета из последней версии недостаточно, а опубликованный ключ нужно отозвать.
4. Выполнить все проверки из [CONTRIBUTING.md](../CONTRIBUTING.md), затем release-проверку
   в новом пустом каталоге вывода, чтобы не столкнуться с существующим архивом.
5. Распаковать полученный архив и открыть его `README.md`: release_check уже проверяет
   локальные ссылки, но перед публикацией стоит визуально просмотреть главную страницу и
   руководства на хостинге.
6. После первого push дождаться Linux и macOS CI. Локальная проверка не подтверждает
   удалённые задания или другую ОС. Для релиза приложить архив и `.sha256`, сохранив
   `release-check.json` как результат конкретной сборки.
7. Не выдавать исторические отчёты и синтетические корпуса за production-аудит. Внешние
   ссылки, адреса поставщиков и условия сторонних моделей проверять перед конкретным выпуском.

Эти действия описывают подготовку, но сами не создают Git-репозиторий, коммит, тег, release
или публикацию на внешнем сервисе.

Установка: сверить SHA-256 с доверенным источником, распаковать архив и поместить `kaponir`
в каталог пользователя в PATH. Затем `kaponir init`, настройка правил и проверка своего корпуса.
Для обновления остановить службу, сохранить резервную копию всего `KAPONIR_HOME` вместе
с `vault.key` и `token.key`, заменить бинарник и выполнить локальную проверку восстановления
на копии данных. Сохранить предыдущий бинарник для отката. Проверка повторного `init` не
является тестом миграции базы с произвольной старой версии.

Резервную копию хранилища делать при остановленном процессе, включая файлы SQLite и ключи.
Копия должна храниться с ограниченным доступом; её пригодность проверяется восстановлением
в отдельном каталоге. Не менять token key при обычном обновлении. Контуры Team/Global пока
задают приоритет правил; они не заменяют отдельные учётные записи и серверную модель ролей.
