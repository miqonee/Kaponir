Kaponir Enterprise — независимая приёмка в Minikube

Ты принимаешь ветку приватного репозитория miqonee/kaponir-enterprise как SRE и инженер интеграционного
тестирования. Сам подними изолированный кластер Minikube, установи в него проверяемую сборку, отправь
реальные HTTP/SSE-запросы через Kubernetes Service, проверь права, сохранность данных и поведение при
отказах. Верни команды повтора и результаты, полученные в этом кластере. Внешний LLM замени управляемым
поставщиком в том же кластере. Шлюз, авторизация, PostgreSQL, сеть, хранение и код восстановления должны
быть настоящими.

Что именно принимаешь

• Вход — Git SHA или ветка с реализацией Enterprise, профиль проверки core либо pilot, ресурсы хоста. Если
  SHA не передан, запиши текущий HEAD и проверь содержимое. Тег Community v1.0.3 указывает на
  9e3a814babadb66790598c6e73d0e6ad971849b1 и служит точкой сравнения. В одном этом теге есть Compose и
  SQLite, но нет Helm-развёртывания Enterprise. Если передали его или требуемой реализации ещё нет, выдай
  BLOCKED с SHA, точным отсутствующим компонентом и командой, на которой остановился. Установка нескольких
  Community-подов с локальными vault не проходит приёмку.
• В публичном miqonee/Kaponir прочитай docs/ENTERPRISE_ARCHITECTURE.md (редакция 10 или новее),
  docs/SECURITY.md и docs/OPERATIONS.md. Контракт маршрутов, chart, values, миграции и команды bootstrap
  возьми из проверяемой ветки Enterprise. Перед запуском запиши SHA Enterprise, полный SHA использованного
  ядра и базовый тег Community. Профиль core
  включает C1–C11 с настоящими HTTP-воркерами, фоновым исполнителем analysis и PostgreSQL. Профиль pilot
  добавляет P1–P8. Для заявленного профиля SSO отдельно обязателен P9. Базовую установку проверяй
  без Redis, KEDA и провайдера идентификации. Укажи в отчёте фактически испытанные конфигурации.
  Пока реализован только core, отчёт может подтвердить только core. Не подменяй приложение тестовой авторизацией
  или SQL-вставками вместо публичных действий пользователя. Для проверки инвариантов годится отдельная
  тестовая read-only роль БД.

Создай воспроизводимый стенд

1. Запиши SHA, версии Minikube, kubectl, Helm, Kubernetes, runtime, PostgreSQL, StorageClass, ОС/архитектуру
  и выделенные CPU/RAM/диск. Проверь драйвер, свободные ресурсы и совместимые версии до запуска. Начальный
  ориентир для одноузлового стенда — 4 vCPU и 8 ГиБ при доступной мощности. Зафиксируй конкретные версии
  образов и digest. Выдели уникальный профиль, отдельные временный kubeconfig и namespace. Все операции,
  особенно остановку компонентов и уборку, адресуй явно этому контексту. Существующие пользовательские
  кластеры, релизы и PVC не затрагивай.
2. Используй реальный chart ветки (предлагаемый путь deploy/helm/kaponir/). Подними PostgreSQL 17
  совместимой исправленной версии с собственным PVC в тестовом StatefulSet или используй эквивалентный
  локальный контролируемый chart. Создай отдельные роли и тестовые Secret, включая сохраняемые версии ключей
  vault. Для генерации и временных файлов используй закрытый рабочий каталог. Не печатай ключи. Подними HTTP
  mock-поставщика в отдельном Deployment и Service. Построй и загрузи образ Kaponir из проверяемого SHA в
  runtime Minikube. Сверь исполняемые роли, запущенные imageID и метки ревизии у HTTP и analysis.
  У HTTP-подов нет доступа к файловому каталогу PostgreSQL. Для C11 выдели второй тестовый кластер
  (например, отдельный профиль Minikube) под внешний PostgreSQL. Запиши оба контекста. Подготовь закрытый
  маршрут и DNS-имя с TLS-сертификатом тестового CA, доступные именно из подов кластера приложения.
3. Включи CNI с реальным исполнением NetworkPolicy, например Calico, и metrics-server для измерений. Примени
  chart с requests/limits, пробами, migration Job, выделенными ServiceAccount и ограниченными сетевыми
  правилами. Дай разрешения на DNS, БД, mock и необходимые административные/метрические соединения строго по
  ролям. Проверь разрешённое соединение и отказ обычному тестовому поду при обращении к закрытому
  внутреннему порту. Сверь RBAC админки для её Deployment/EndpointSlice и отсутствие доступа на чтение
  произвольных Secrets. Для TLS используй тестовый доверенный CA, если он нужен контракту. Весь LLM-трафик
  стенда идёт только к mock. Внешние S1 и OCR для core выключены. В pilot используй локальное распознавание
  либо явно доверенную стендовую заглушку для проверки политики.
4. Дай одну команду повторного запуска (например, scripts/test_enterprise_minikube.sh с --ref и --suite),
  отдельно команду уборки. Названия в примере ниже — переменные, которые заполняет твой runner. Файл
  значений ссылается на Secret по имени. Для прогона с готовым подключением до Helm подготовь namespace,
  БД, mock и тестовые доступы, затем сверь Job, поды, PVC, EndpointSlice и версию миграций. В C11 дождись
  доступности первичного мастера до настройки БД, затем пройди форму и проверь запуск рабочих подов. При
  неподдерживаемом драйвере или ошибке запуска приложи конкретную причину.

   export KUBECONFIG="$RUN_DIR/kubeconfig"
   minikube start -p "$PROFILE" --driver="$DRIVER" --kubernetes-version="$K8S_VERSION" --cni=calico --cpus="$CPUS" --memory="$MEMORY_MB"
   minikube -p "$PROFILE" addons enable metrics-server
   minikube -p "$PROFILE" image load "$IMAGE"
   helm lint "$CHART" -f "$VALUES_FILE"
   helm template kaponir "$CHART" -n "$NS" -f "$VALUES_FILE" > "$RUN_DIR/rendered.yaml"
   helm upgrade --install kaponir "$CHART" --kube-context "$PROFILE" -n "$NS" -f "$VALUES_FILE" --wait --wait-for-jobs --timeout 10m
   kubectl --context "$PROFILE" -n "$NS" get deploy,sts,jobs,svc,pvc,endpointslice

Данные и независимые наблюдения

Создай через штатный административный интерфейс организации Atlas и Birch. У Atlas есть команды Orion и
Vega, Иванов и Петрова в Orion, Белов в Vega, ключи IDE/CLI Иванова и отдельная служебная запись CI. У Birch
зарегистрируй такой же логин ivanov. Определи тестовое личное значение, один общий код Orion, корпоративный
домен и свежие синтетические секреты для каждого запроса. Используй пути
/home/group.demo/ivanov/work/build.log и C:\Users\ivanov\a.txt, контрольный /srv/ivanov-tools/log и пример с
password/secretKey/accessKey в values.yaml. Отдельный безопасный фрагмент обязан дойти без лишней замены.

Mock умеет возвращать полученный токен, заранее заданный токен раннего запроса, JSON, поток SSE с
разрезанным токеном, финальный usage или его отсутствие. Для pilot добавь tool calls, Anthropic, задержку
первого токена, 429 и управляемый обрыв до/после первого фрагмента. Ведёт закрытый счётчик фактических
вызовов и проверяет полученное тело/заголовки по синтетическим маркерам. Для каждого случая сопоставь
фактическое тело у поставщика, ответ конкретному клиенту и записи в БД и аудите. В отчёт вынеси ID случая и
результат сравнений. Оригиналы, ключи, cookie, дампы БД и содержимое Kubernetes Secrets в отчёт не включай.

Обязательная матрица core

C1. Установка и идентичность. Пройди bootstrap с чистой БД, повтори установку/миграции без дублей. Через Web
  UI создай Иванова, выдай ключ, войди сотрудником в отдельном браузерном контексте и проверь его личную
  статистику. Тот же ключ не открывает чужие карточки, административные API, правила и исходные находки, в
  том числе по известному URL тестовой записи. Проверь отсутствие чужих данных и в счётчиках. Каталог
  /v1/models и прямой маршрут /p/{id}/v1/chat/completions соблюдают общую политику организации, команды и
  ключа. Для запрещённой модели, просроченного ключа и чужой организации подтверди отказ и нулевой прирост
  счётчика mock. Проверь явный отказ закрытого маршрута и отправку неподдерживаемого вложения через открытый
  маршрут с обязательной защитой. Ни один из этих двух вызовов не должен дойти до mock.

C2. Маскирование и раскрытие через разные поды. Сначала пройди полный путь через обычный Service. Затем
  подними как минимум две HTTP-реплики. Подай первый запрос на конкретный готовый под A и следующий на B,
  через отдельные разрешённые внутрикластерные подключения или адресные port-forward для диагностики. Прямой
  доступ сохраняет обычную аутентификацию и TLS. Установи один session ID. Во втором запросе нет исходного
  значения. Mock возвращает ранее увиденный токен. В авторизованном журнале сверь два разных pod UID. Для
  Иванова восстанови исходный текст, для Петровой разреши командный токен, для Белова сохрани личный и
  командный токены чужого контура. Разрешённый корпоративный токен восстанавливается внутри Atlas.
  Пользователю Birch оригиналы Atlas недоступны даже при совпадении логина или session ID. Проверь
  неизвестный токен и литерал, уже похожий на токен, обычный JSON и SSE с токеном, разделённым между
  событиями и транспортными порциями. Сравни итоговую строку, включая Unicode и отсутствие оборванных частей
  токена. По синтетическим маркерам проверь, что защищённые оригиналы и секреты входных ключей отсутствуют в
  теле/заголовках у mock, технических логах, метриках и трассировке. Сохрани только результаты сравнений.

  Проверь доставку корневого ключа отдельно. В тестовом namespace создай Secret со свежим синтетическим
  ключом. Первый под получает его через secretKeyRef в KAPONIR_VAULT_KEY и сохраняет соответствие. Замени
  под и восстанови старый токен с тем же ключом через KAPONIR_VAULT_KEY_FILE из смонтированного Secret.
  Проверь, что на постоянном томе нет сгенерированного vault.key, а у воркера без доступа к vault нет секрета.
  Реплика с неверным, отсутствующим или одновременно заданным двумя способами ключом должна остаться
  вне readiness. Восстанови правильную конфигурацию и проверь прежний токен. Если проверялся только
  Kubernetes Secret, укажи это в отчёте. Интеграцию с HashiCorp можно подтвердить отдельным прогоном
  с установленным Vault Secrets Operator или Agent Injector.

C3. Владение, гонки и смена прав. Белов отправляет путь Иванова. В событиях отправитель — Белов, владелец
  префикса — Иванов. Суффикс проверяется отдельно, а контрольный путь с ivanov-tools не получает владельца
  только по подстроке. Одновременно подай одно новое значение через два пода в один vault. Независимая
  проверка должна найти одно соответствие и корректный каталог. Повтори для одинакового значения в двух
  личных vault и проверь раздельные права и записи. Проверь коллизию правил с обязательным корпоративным
  действием. Повтори доставку события с тем же стабильным ID через предусмотренный механизм повторной
  обработки. Затем создай новое отдельное вхождение. Проверь соответственно одно и два вхождения по
  стабильным ID.

C4. Отзыв и перевод. Выпусти новый ключ Иванову, отзови старый и сделай новые обращения к каждому HTTP-поду.
  Старый ключ и связанная браузерная сессия теряют доступ, новый ключ раскрывает прежний личный токен.
  Переведи сотрудника из Orion в Vega. Новые вызовы учитываются с актуальной командой и разрешённым ключом,
  право раскрывать старый командный токен Orion пропадает. Личный vault и принадлежность старых событий
  сохраняются. Проверь отдельно отключение пользователя с несколькими ключами.

C5. Масштабирование и контролируемые отказы. Под непрерывным трафиком выполни 1 → N → 1, N задай параметром
  (например 3). Контролируй готовые EndpointSlice и фактические UID. Одна keep-alive связь может попадать на
  один под, равных долей трафика не требуй. Открой поток, который укладывается в grace period, и начни
  плановый вывод обслуживающего пода. Дождись завершения потока и проверь восстановление на другой реплике в
  следующем запросе. Затем принудительно прерви тестовый длинный поток. Найди причину в истории и убедись по
  счётчику mock, что второго исполнения не было. Останови только Deployment админки и продолжай запросы.
  После её запуска найди накопленные события. В своём стенде временно останови PostgreSQL или контролируемо
  лиши приложение записи. Используй новый секрет, проверь ограниченное ожидание, снятие readiness,
  жизнеспособный процесс и ноль новых обращений к mock до надёжной записи. Верни БД, проверь автоматическое
  восстановление готовности и прежних токенов. При отсутствии всех готовых эндпоинтов фиксируй результат
  Service и отдельно состояние пода.

C6. Перезапуск и резервное восстановление. Перезапусти PostgreSQL с тем же тестовым PVC, замени HTTP-поды.
  Проверь ранее выданный токен и сохранённый отзыв. Смени рабочую версию ключа шифрования по процедуре ветки
  и проверь чтение старой и новой записи на разных подах. Затем сделай согласованный backup, зашифрованный
  при хранении, сохрани ссылки на нужные версии ключей и восстанови в отдельную БД/namespace. Оригинальный
  PVC стенда останется доступным. В копии с правильными ключами проверь старый токен, изоляцию и аудит, с
  отсутствующей версией ключа — контролируемый отказ. Зафиксируй затраченное время и точку восстановления.
  Это отдельная проверка помимо рестарта пода.

C7. Измерение скорости. Запусти генератор нагрузки отдельным Kubernetes Job через Service. Port-forward
  используй только для отладки и UI. Зафиксируй seed, лимиты подов и PostgreSQL, PVC, источник трафика и
  задержки mock. Включи, например, входы 1, 10 и 100 КиБ с известными, смешанными и новыми значениями.
  Чередуй обычные ответы и SSE. Проверь корректность восстановления под нагрузкой. Возьми одинаковую смесь
  при одной и нескольких репликах, прогрев 30 с, затем минимум три одинаковых измерения по 60 с на каждой
  выбранной параллельности (например 1, 8, 32 в пределах ресурсов). Покажи предложенную и фактически
  завершённую нагрузку, число образцов, запросы/с, p50/p95/p99, ошибки по типам и поведение при насыщении.
  Раздели mask, restore, ожидание БД/пула, первый токен upstream и полную задержку. Приложи CPU, память,
  очереди, использование ресурсов генератором и mock. Укажи изменение общего бюджета CPU при росте N, измерь
  mock напрямую как контроль. Отсутствующую метрику пометь явно. Порог производительности применяй только
  если дан SLO. Ошибочное раскрытие, потерянное соответствие, неверный ответ или дублирование в штатном
  режиме проваливают функциональную приёмку при любой скорости.

C8. «Защита запроса» через реальную переписку и Playwright. В одном вопросе положи тестовый secretKey
  в исходник, а второй уникальный маркер чувствительного типа добавь только в ответ mock. По завершении
  запусти штатную локальную проверку с разрешённым сохранением тестовых фрагментов. Сверь на одном экране
  и через журнал mock, что вместо первого значения ушёл токен, второе встретилось лишь в ответе, а рядом
  с находкой указан настоящий локальный обработчик. Между состояниями «Не запускалась» и «Завершена,
  находок нет» должна быть разница. Для отдельного вызова без достаточных исторических данных проверь
  «Неизвестно», для заблокированного до отправки — ноль обращений к mock. Открой попытку повторно после
  смены политики и проверь неизменность её фактов. Проверь права сотрудника и администратора без права
  раскрытия в браузере и по прямому API. Сохрани обезличенный скриншот одной карточки со всеми этапами.

C9. Ручное масштабирование HTTP из админки. В браузере войди как оператор, открой «Воркеры», выбери HTTP
  и через «Изменить число воркеров» задай две реплики при одной работающей. Сверь изменение Deployment/scale,
  новый pod UID, готовность EndpointSlice и запрос через Service на новом поде. Верни одну реплику тем же
  действием в браузере. Для обоих изменений сверь без перезагрузки страницы желаемое и фактически готовое
  число, автора и итог в аудите. kubectl служит независимым наблюдателем этих двух операций. Повтори
  с правом только на просмотр и проверь отказ сервера и неизменность масштаба. При нехватке ресурсов
  в тестовом namespace проверь видимость причины Pending, затем верни рабочую конфигурацию.

C10. Работа общего ядра и отдельного analysis. Пропусти через Community и Enterprise одной ревизии одинаковые
  синтетические сообщения с одинаковой политикой, областями и детекторами. Сверь типы и позиции замен,
  сохранность открытых участков и восстановленный JSON/SSE. Разные ID токенов у независимых vault допустимы.
  В Enterprise включи разрешённое сохранение исходника тестового вопроса с одним заранее размеченным
  кандидатом для разбора. Через админку поставь этот завершённый вопрос в очередь analysis. Сверь ID задания
  и UID захватившего его пода. На тестовой задаче прерви под после захвата до фиксации результата.
  После истечения аренды дождись обработки другим UID. Из задания открой находку. Сверь реальный фрагмент,
  источник, сотрудника, команду, ключ и версию политики с ожидаемыми. Проверь в БД одно завершение и одно
  вхождение для данного источника. Отдельно проверь понятный результат при удалённом исходнике. Сотруднику
  другой организации задача и находка недоступны. Сопоставь UID и статус с экраном «Воркеры».

C11. Внешний PostgreSQL в другом кластере и «Настройки → База данных». Установи в кластере приложения
  отдельный чистый релиз в режиме внешней БД. Убедись, что в этом релизе нет StatefulSet и PVC для
  PostgreSQL, а мастер доступен при отсутствии подключения. Открой его в браузере с одноразовым доступом.
  Введи адрес БД второго кластера, порт, имя, пользователя и тестовые учётные данные. При неверном CA,
  ошибке входа или недоступной сети одной роли проверь причину, отсутствие новых таблиц и записей Kaponir.
  С исправленными параметрами проверь, что «Проверить подключение» только читает состояние. После изменения
  проверенного адреса «Применить» требует новой проверки. С верным адресом выполни первую инициализацию
  и дождись готовности admin, HTTP и analysis. Перезапусти админку,
  проверь, что одноразовый доступ погашен, подключение сохранилось, а пауза БД не открывает первичный мастер.
  Штатно создай сотрудника, правило и обратимую подстановку. Повтори через разные реплики рабочий путь C2.
  Во время трафика проверь ошибочное подключение. Старый токен должен восстанавливаться через действующую
  БД. Проверь смену учётных данных к той же БД. Пустая, чужая и устаревшая цели отклоняются при замене
  рабочей БД. По процедуре C6 подготовь свежую копию при остановленных записях, переключи подключение
  из админки и сверь версию на всех ролях. Сделай новую запись и независимо проверь, что она появилась
  только в новой БД. Старый токен восстанавливается, поставленные задания и отзыв ключа сохраняются.
  Пароль и полная строка подключения отсутствуют в ответах API, истории операций и логах. Проверь права
  сотрудника и администратора одной организации на чтение параметров и изменение через UI и API. Только
  право на управление БД всей установки допускает эти действия. Уборку обоих профилей адресуй явно тестовым
  контекстам.

Дополнительная матрица pilot

P1. Полноценная админка и фоновые задания. Проверь список всех HTTP-воркеров, desired/ready/fresh, версии
  политики, свежесть после трёх пропусков опроса и снимок при переподключении браузера. Один сотрудник с
  двумя активными запросами — один человек и два запроса. Приостанови обновления для чтения. В живом списке
  различимы ожидание БД, маскирование и ожидание первого токена. Проверь журнал «вопрос → вызовы → попытки»,
  служебный вызов названия и связанные инструменты. Проведи одну находку из HTTP-запроса и одну из документа
  через отдельную фоновую очередь, прерви и возобнови задание. Для импорта без известного автора UI
  показывает неизвестное происхождение. При включённом HPA измени границы HTTP в админке и сверь поля HPA
  и число готовых реплик под нагрузкой при доступном источнике метрик.

P2. Разбор, история и опциональный датасет. На desktop пройди от live-запроса до выделенного фрагмента.
  Задай пересекающиеся фильтры отправителя, команды, ключа и vault. Сверь число доступных вхождений.
  Несовместимая пара фильтров должна дать пустую выдачу. Различи фактический vault и будущую область,
  проверь «принять», «исправить», «отклонить», «отложить», переход к следующей карточке и новую версию
  правила у всех готовых реплик. Найди автора и старую версию в аудите, затем проверь новое маскирование
  через другой под. При modules.dataset.enabled=true проверь ручной черновик, экспорт JSONL и автосбор после
  явного включения. Выключи модуль Helm upgrade при непустой очереди и открытом старом клиенте. После
  вступления настройки в силу попробуй записать пример из старой вкладки и задания. Проверь ответы 404,
  отсутствие новых примеров в БД и браузере, в том числе от воркера со старой конфигурацией при обновлении.
  Кнопки «В датасет» и флажка нет, старая закладка открывает находки. Аудит и публикация правил работают.
  Вновь включи модуль и прочитай прежний пример.

P3. Протоколы и защита изображений. Повтори границы доступа для Anthropic Messages/count_tokens, tool calls,
  sidecar anonymize/deanonymize и /api/v1/deanonymize/stream. Для последнего передай последовательные части
  одного потока разным подам по контракту ветки. На синтетическом изображении с двумя вхождениями секрета
  проверь по пикселям копии у mock, что обе области непрозрачно закрашены, а безопасная область читается.
  При ошибке включённой защиты вложение и запрос не покидают шлюз. Команда пользователя «кпн открой» не
  раскрывает обязательную корпоративную маску. Проверь, что включение внешнего анализа или сохранения
  оригинала требует соответствующей политики.

P4. Модели и деньги. Одновременно с двух HTTP-подов начни два вызова, каждый из которых по отдельности
  помещается в остаток бюджета, а вместе — нет. Ровно одна попытка финансируется и доходит до mock. Повтор
  финального события/usage не даёт второго списания. Потеря usage после отправки оставляет резерв на сверке,
  сумма не обнуляется. Сверь учёт по команде, ключу, вопросу и попытке, входные/выходные/кешированные токены
  и архивную версию тарифа. Поочерёдно смоделируй 429 разрешённого подключения, отсутствие подходящего
  резерва и разрыв после первого SSE-события. Проверь число вызовов и отсутствие повтора после начала
  выдачи. Для профиля orion/auto проверь допустимую модель, квоту, инструменты и зону данных. Многошаговый
  orion/agent и canvas проверяй отдельным профилем только после появления реализации.

P5. Поздний пропуск и получатели данных. Задай два независимых внутрикластерных стендовых получателя с
  отдельными журналами — основную модель и анализатор, объявленный внешним в политике стенда. Разреши
  ему получить тестовый фрагмент. Передай вымышленное название проекта, которое политика этого запроса
  пропускает. Фоновая проверка после ответа находит название в исходнике. Через UI и фактические тела у
  обоих получателей подтверди, что исходное название ушло основной модели и отдельно анализатору.
  Прими правило, повтори запрос и сверь токен только в новой попытке. Проверь также защищённое значение,
  найденное повторно после ответа, и одинаковый текст в двух вызовах с разными получателями. Ни одно
  вхождение не должно заимствовать вывод о раскрытии у другого. При обрыве с неопределённым исходом
  сверяй отображённую неопределённость с журналом попыток.
  На отдельных синтетических кандидатах сравни внешний S1 L0 (признаки) и разрешённый L1 (исходная
  строка) по принятым полям. Повтори с внутренним API и тем же именем модели. Смена места обработки и
  включение внешнего анализа только для следующего запроса не переписывают старые карточки.
  С отключённым внешним анализом счётчик второго получателя должен остаться прежним. Сверь статусы
  завершения, ошибки фоновой проверки и отсутствия находок. Реальные внешние сервисы для теста не нужны.

P6. Redis для сессий. Сначала пройди основной сценарий C2/C4 без Redis. В конфигурации с Redis заполни
  кеш запросом к A, запусти новый HTTP-под B и через него продолжи сессию. Убедись по счётчикам, что B
  воспользовался общей записью. Проверь разделение организаций при одинаковом ID сессии. Останови Redis,
  повтори запросы, проверь ограниченный переход к PostgreSQL, восстановление прежнего токена у владельца
  и отказ после отзыва. Попадание в прогретый кеш при отключённой БД не даёт ни вызова mock, ни права
  раскрыть оригинал. В профиле RDB/AOF с PVC восстанови Redis после рестарта и проверь истёкшие TTL,
  старые версии и сохранность отзыва. С одними и теми же данными сравни время прогрева, hit/miss,
  обращения к БД, память и p95/p99 при выключенном, холодном и тёплом кеше. Если опция не установлена,
  так и отметь в отчёте выбранной конфигурации. При заявленной приёмке этой опции пройди оба режима.

P7. Независимые очереди analysis, ocr.batch и ocr.inline. Подай очередь тестовых PDF и покажи, что очередь
  растёт у kaponir-ocr-batch. В админке увеличь только этот ручной пул. Проверь захват свободной работы
  новым подом и неизменность соседних пулов. Тем же экраном уменьши размер, проверь желаемое и готовое
  число. Пройди увеличение и уменьшение для analysis и ocr.inline в допустимых пределах. Если включён KEDA,
  измени из админки границы пакетного OCR, сверь их в ScaledObject и проверь рост и уменьшение числа
  потребителей по метрике очереди, включая запуск с нуля. Пока batch занят, пошли текст и отдельное интерактивное вложение.
  Сравни очереди и фактические задержки, проверь содержимое у mock. Задержи потребителя за пределы аренды
  на контролируемой задаче. Новая попытка заканчивается один раз, а запись старой попытки после возобновления
  отвергается. Проверь ограниченные повторы, терминальную ошибку и ожидание дочернего OCR без занятия
  слота анализа. Останови только интерактивный OCR: запрос с обязательной защитой завершится по дедлайну,
  счётчик вызовов поставщика для него останется нулевым, текст продолжит обслуживаться. Поздний результат
  и ошибка одной страницы PDF не приводят к отправке исходника. Возврати размеры всех пулов.

P8. Дашборды и контроль. Возьми готовые трассы из C8/P5, включая случай с открытым названием «Северка»,
  находку только в ответе и внешнюю передачу признаков. Сверь виджет «Что не успели скрыть» с журналами
  обоих mock и независимой выборкой. Повтор события, защищённое вхождение, неопределённый исход и событие
  другого tenant не увеличивают его числитель. Проверь покрытие проверки и переход с виджета к нужной
  попытке. Пройди из обзора в пулы, очередь OCR, работу пода и историю запроса, затем в расходы команды
  и задержку зависимости. Приостанови захват пакетных заданий, проверь завершение активного, возобнови
  захват и повтори терминальную ошибку через разрешённый API. В каждом случае сверь права, изменение в БД
  и аудит. Останови heartbeat одного потребителя, затем восстанови: устаревшее измерение отличается от нуля.
  Для профиля с GitOps инициируй изменение числа или границ реплик через UI. Сверь состояние в источнике
  конфигурации, результат синхронизации и фактическое состояние пула. Отчёт отдельно указывает испытанные
  режимы ручного управления, HPA/KEDA, GitOps и Redis с диском или без него.

P9. Опциональный SSO портала. Подними локальный OIDC-провайдер стенда, например Keycloak. Через
  «Настройки → Вход и SSO» выбранной организации настрой тестовый
  issuer, доступный браузеру и серверу по одному HTTPS-адресу, клиент с точным redirect URI и доверенный
  тестовый CA. Используй синтетические аккаунты и настоящий вход в провайдер через браузер. Привяжи
  Иванова и оператора к существующим ID в Atlas через штатный интерфейс. После входа через компанию
  сверь ID сотрудника, прежний личный vault и доступ Иванова только к своей статистике. У оператора
  сохраняется назначенное право на управление воркерами. Повтори вход после смены почты. Отдельная
  непривязанная запись с таким же email в другом issuer не получает доступ Иванова.
  Включи обязательный SSO для Atlas. Новая и ранее открытая браузерные сессии по ключу не дают доступа,
  IDE с тем же действующим ключом продолжает запросы. В Birch по-прежнему работает её способ входа.
  При недоступном IdP проверь ясную ошибку нового входа и работающий шлюз. Верни IdP, отзови один IDE-ключ
  и проверь независимую SSO-сессию. Заблокируй сотрудника в Kaponir и повтори обращения из открытой
  SSO-сессии и по другому его ключу. Оба отклоняются. На отдельном аккаунте задай короткий срок до повторного
  входа, отключи его только у IdP и проверь отказ по истечении срока. Проверь аудит и отсутствие токенов, cookie и кодов
  в технических логах. В отчёт сохрани только результаты сравнений и обезличенные идентификаторы.

Автоматическая приёмка обновления Enterprise

На первой устанавливаемой сборке агент выполняет C6 и сверяет kaponir --version внутри готового пода
с заявленной версией сборки. В отчёте укажи SHA и фактический imageID. У первой сборки пока нет
предшественника для проверки обновления. Как только доступны две поддерживаемые корпоративные сборки,
выполни отдельный прогон на паре исходной и целевой ревизий. Если прогон обновления запрошен явно,
отсутствующую исходную сборку укажи как BLOCKED для этого прогона.

1. Установи исходную сборку. Штатным запросом получи подстановку, сохрани её для проверки. Выдай
   сотруднику второй API-ключ, отзови первый, затем сделай согласованную резервную копию БД и обеспечь
   доступ к нужным версиям ключей vault.
2. Штатно обнови приложение и chart до целевой ревизии поверх этих данных. Сверь версию в готовых подах
   и завершение миграции. Верни старую подстановку через mock и проверь по API, что владелец получил
   оригинал, коллега без права раскрытия получил токен, а отозванный API-ключ отклонён.
3. В отдельном namespace восстанови предрелизную копию по документированной процедуре. Подними совместимую
   версию приложения и повтори те же проверки. Сохрани в отчёте обе ревизии, версии приложения и схемы,
   результаты запросов и время восстановления. Сам прогон может выполнять агент без участия оператора.

Отчёт и правила оценки

Сохрани компактный отчёт для человека и машиночитаемый JSON или JUnit. Для каждого ID укажи ожидаемый
результат, факт, длительность, число обращений к mock и обезличенную ссылку на доказательство (UID пода,
технический request ID, diff счётчика, скриншот на синтетике). В случае сбоя приложи отредактированные
события и логи только относящихся к нему компонентов. Различай PASS, FAIL и BLOCKED. Пропуск обязательного
теста не даёт зелёного результата. Возвращай код 0 при успешной приёмке выбранного профиля, код 1 при
нарушении контракта, код 2 при недостающей предпосылке. Если упал сам тестовый runner, исправь его и повтори
сценарий. При нарушении контракта продукта сохрани воспроизводимый пример с исходным критерием приёмки.

В финале сообщи SHA и команду воспроизведения, какие проверки прошли, где возникло первое ограничение
нагрузки, какие данные нужны перед корпоративным пилотом. Храни отчёт вне удаляемого namespace. Удали или
останови только созданный этим прогоном профиль по выбранному режиму уборки. Замеры на одноузловом Minikube
характеризуют эту машину. Для отказа целого узла, HA PostgreSQL и production SLA требуется отдельное
многонодовое испытание.

Что измерить для оценки продукта на корпоративном пилоте

Передай владельцу пилота три измеримых предложения отдельно от автоматического результата Minikube.
Владелец данных утверждает ожидаемую разметку отложенного корпуса организации. После этого агент на каждой
сборке автоматически сравнивает фактическое тело у тестового поставщика с разметкой и считает критические
пропуски до отправки и лишние маски по классам. Поздняя находка не засчитывается как своевременная защита.
Для проверки понятности интерфейса дай пяти новым администраторам
по незнакомому запросу. Предлагаемый ориентир — хотя бы четверо за 30 секунд без подсказок правильно
назовут, что ушло основной модели и что видел анализатор. Отдельным действием пусть исправят один пропуск
и проверят следующий запрос. Для эксплуатации согласуй с командой пиковый RPS и бюджет добавленной
шлюзом задержки p95/p99, затем проверь их на целевом железе и диске. Для каждого замера укажи выборку,
условия и факт измерения.
