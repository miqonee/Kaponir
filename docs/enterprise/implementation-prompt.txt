Kaponir Enterprise — первый работающий этап

Работай в приватном репозитории miqonee/kaponir-enterprise как инженер Rust, PostgreSQL и Kubernetes. Реализуй
первый сквозной сценарий Enterprise от выдачи ключа до восстановления ответа другой репликой и разбора
завершённого вопроса фоновым воркером. Поставь исполняемые роли HTTP и analysis, схему БД, минимальный
Web UI и устанавливаемый Helm chart. Этап 1 ниже — объём
реализации. Раздел «Дальше» задаёт контракты для следующих этапов. Результат должен принимать независимый
инженер по известному Git SHA.

Отправная точка

1. Зафиксируй SHA рабочей ветки Enterprise и отдельно полный SHA используемого общего ядра из
  miqonee/Kaponir. Серверные роли, админку и chart поставляй из приватного репозитория. Подключи общие
  Rust-крейты с зафиксированной ревизией. Community v1.0.3 на 9e3a814babadb66790598c6e73d0e6ad971849b1
  служит исходной точкой сравнения. В публичном репозитории прочитай
  docs/ENTERPRISE_ARCHITECTURE.md (редакция 10 или новее), docs/SECURITY.md, docs/OPERATIONS.md,
  docs/COMMANDS.md, docs/S1.md, docs/IMAGE_PROTECTION.md и docs/ROADMAP.md. В спорных местах сопоставь план с кодом и
  запиши принятое решение. Не выдавай план или стендовый прототип PostgreSQL за готовую реализацию.
2. Проследи один настоящий запрос через crates/kaponir-proxy/src/server.rs, state.rs, openai.rs, sse.rs и
  crates/kaponir-core/src/vault.rs до crates/kaponir-vault. В v1.0.3 есть синхронный контракт Vault, конкретный
  SqliteVault и общее состояние под Mutex. Найди обращения к SQLite в журнале, настройках, сессиях и UI.
  Подключение PostgreSQL в одном обработчике не переводит на него остальные пути. Переиспользуй движок
  правил, форматы токенов и потоковый декодер. Пакетируй обращения к БД, ограничь пул. Не держи транзакцию,
  соединение БД или блокировку движка при ожидании провайдера либо клиента SSE. Сетевой I/O не должен
  блокировать executor Tokio.
3. Режим Community по умолчанию сохраняет локальный SQLite, kaponir serve, существующие CLI, Compose, Web UI
  и формат данных. Перепроверь установку с kaponir init --without-dataset и Compose с
  KAPONIR_DATASET_ENABLED=false. Для Enterprise введи явный режим запуска и проверку обязательной
  конфигурации при старте. Неверная строка подключения или недоступный ключ в Enterprise должны останавливать
  обработку. Автоматический переход на локальную БД создаст расходящиеся данные.

Этап 1. Что должно заработать

Администратор создаёт организацию, команды Orion и Vega, сотрудника ivanov в Orion и выдаёт ему ключ IDE.
Создаются личный vault и первое точное личное правило для логина. Иванов отправляет запрос через общий
адрес. Тестовый поставщик получает маску, а Иванов получает исходное значение даже в потоке, где токен
пришёл частями. Следующий запрос той же сессии попадает на другую реплику. Она восстанавливает прежний токен
без исходного текста первого запроса. Сотрудник другой команды получает этот же токен в ответе поставщика и
видит его замаскированным. Отключение админки не прерывает работу шлюза. После отзыва ключа новые запросы
отклоняются всеми репликами.

  контекстом запроса и правами, адаптером хранения PostgreSQL, исполнением задач и телеметрией.
  На одном наборе синтетических примеров с одинаковыми правилами, владельцами и детекторами проверь
  обе редакции. Сверяй типы, участки маскирования, сохранность открытых участков и восстановленную строку

• Поставь реальный HTTP-воркер и один рабочий тип задания в отдельном процессе kaponir-analysis.
  Оператор в админке ставит завершённый вопрос на проверку. Проверь его полномочие и наличие разрешённого
  политикой сохранённого источника. Свяжи задание с исходными организацией, сотрудником, командой, ключом
  и запросом. Исполнитель берёт работу из PostgreSQL по контракту аренды ниже. Перед чтением проверь
  область доступа и срок хранения источника. Для уже удалённого исходника верни понятный статус.
  Вызови общий движок с опубликованной политикой, зафиксируй версию и запиши
  находку и завершение в одной транзакции. При повторной доставке вхождение остаётся одно. Открой результат
  из задания в «Находках». Документный worker Community и специализированные пулы OCR имеют свои роли.

Хранилище и полномочия

• Одна логическая БД PostgreSQL. Общая схема содержит организации, сотрудников и служебные учётные записи,
  команды и членство, входные ключи, реестр vault, каталог токенов, опубликованные политики, сессии, попытки
  провайдера, события разбора и аудит. В целевой архитектуре у каждого vault своя схема внутри этой БД. 100
  сотрудников и 10 команд в одной организации дают 111 логических vault. Личный vault принадлежит сотруднику
  независимо от количества и ротации его API-ключей. Материализуй необходимые для этапа таблицы с
  ограничениями и индексами. Реестр связывает внутренние идентификаторы и имена схем. Идентификатор схемы
  берётся только из доверенного реестра. Условия выборки, внешние и уникальные ключи сохраняют границы
  организации. Контекст запроса не должен пережить возврат соединения в пул.
• Для вызовов шлюза права определяются сервером по входному ключу, текущему членству и политике. Пользовательские поля, ID
  сессии, токен маски и выбранный прямой маршрут не удостоверяют владельца. Каждый входной ключ принадлежит
  одному человеку или служебной записи и одной команде для атрибуции. Несколько ключей IDE/CLI разрешены.
  Храни безопасный публичный ID, проверочный отпечаток высокоэнтропийного секрета, назначение, срок и отзыв.
  Покажи секрет один раз. Первого администратора создавай ограниченной установочной процедурой, повторный
  запуск должен быть безопасен. В базовой установке обменивай ключ по TLS на ограниченную серверную сессию с
  защищённой cookie, CSRF-защитой изменений и отзывом. Храни у браузерной сессии постоянный ID сотрудника,
  организацию, способ входа и для входа по ключу его ID. Это позволит добавить SSO без смены владельца vault.
  Раздельно храни входной API-ключ сотрудника,
  исходящие учётные данные поставщика и ключевой материал vault.
• Для каждого совпадения отдельно определи приоритет правила, владельца значения и право текущего
  пользователя на раскрытие. Приоритет — обязательное корпоративное, обычное корпоративное, командное,
  личное, встроенный детектор. Точный логин и префикс зарегистрированного домашнего каталога принадлежат
  Иванову даже в запросе Белова. В /home/group.demo/ivanov/work/build.log скрой личный префикс и отдельно
  проверь work/build.log. На Windows проверь целый компонент в C:\Users\ivanov\a.txt. В
  /srv/ivanov-tools/log одного фрагмента имени недостаточно. Неоднозначность отправляй на разбор. Модель не
  может расширить круг получателей. Обязательное правило действует и для команды «кпн открой». После
  перевода сотрудника его старые события сохраняют прежнюю команду, раскрытие учитывает текущие права.
• Оригиналы шифруй аутентифицированным шифрованием с версией ключа и уникальным nonce, привязывай ciphertext
  к организации, vault и записи. Для поиска нужен отдельный ключ слепого индекса (по плану HMAC). Не
  используй входной API-ключ для шифрования. Дай оператору процедуру смены активной версии ключа. При
  ротации обеспечь чтение старых записей и дедупликацию при смене индекса. Секреты поставщика, ключи vault и
  учётные данные PostgreSQL подавай по ссылкам на секреты. В пилоте допустимы выделенные Kubernetes Secrets
  с ограниченным RBAC. Опиши интеграцию с KMS и восстановление прежних версий ключей.
  Для корневого ключа поддержи контракт Community. KAPONIR_VAULT_KEY содержит 64 hex-символа,
  KAPONIR_VAULT_KEY_FILE указывает на файл с таким значением. Для Enterprise требуется один источник
  на процесс с доступом к vault. В Helm указывай secretKeyRef для Kubernetes Secret, синхронизируемого
  из HashiCorp Vault, либо путь к файлу Vault Agent. Все уполномоченные реплики должны использовать
  согласованные версии. Проверяй ключ до readiness и записи данных. На ошибке сообщай причину без значения
  секрета. Привяжи это к указанной выше процедуре ротации и восстановления из резервной копии.
• Одна транзакция выделяет или переиспользует токен и фиксирует обратимое соответствие и запись в каталоге.
  Уникальность должна выдерживать одновременную вставку с разных подов. Учитывай организацию, vault, тип,
  канонизацию и стратегию, обрабатывай коллизии и зарезервированные литералы в формате токена. Сначала
  commit, затем вызов поставщика. При неуспешном commit число новых вызовов поставщика равно нулю.
  Неизвестный, изменённый или недоступный токен остаётся токеном. Полная история сообщений опциональна для
  аудита. Для восстановления достаточно соответствий, версий ключей и прав.

Шлюз, учёт и интерфейс этапа 1

• Проведи через обычный публичный Service как минимум OpenAI Chat Completions с JSON и SSE, каталог
  /v1/models и соответствующие /p/{id}/v1/... . Каталог и прямой маршрут применяют пересечение политик
  организации, команды и входного ключа. Для первого этапа достаточно одного разрешённого подключения и
  явного списка моделей. У поставщика отдельный исходящий секрет. Не пересылай ему внутренние заголовки,
  входной ключ или служебную cookie. В Enterprise все остальные точки входа Community, включая Anthropic, sidecar
  restore, старые административные API, экспорт и задания, либо проходят те же серверные проверки, либо
  закрыты до своей реализации. Та же граница действует внутри разрешённого маршрута. Для неподдерживаемого
  вложения или типа содержимого выбери явную ошибку до вызова поставщика, если шлюз не может применить
  требуемую политику. Задокументируй матрицу маршрутов, типов содержимого и отказов. Настройка
  неподдерживаемого ограничения бюджета должна явно отклоняться.
• Пиши событие маскирования вместе с результатом его обработки в БД. Завершение внешнего вызова фиксируй
  отдельно. Стабильные ID запроса, вхождения и попытки делают повторную доставку идемпотентной. Различай
  повторную доставку того же события и новое осознанное обращение пользователя. В журнале фиксируй выдачу и
  отзыв ключа, изменение членства, решение по правилу и доступ к оригиналу. Рабочей роли выдавай лишь
  необходимые права записи аудита. До отправки зафиксируй организацию, ключ, сотрудника, команду на тот
  момент, вопрос, сессию, версию политики и маршрут. Один вопрос может включать несколько обращений.
  Фиксируй результат каждого вызова и фактический usage, когда он есть. При отсутствии usage укажи
  «неизвестно». Полные сообщения и оригиналы вложений сохраняются только по политике доступа и хранения. Для
  технических логов и метрик достаточно длительностей, статусов и агрегатов.
• В минимальной админке должны работать создание и отключение сотрудника, назначение и смена команды,
  выдача/отзыв ключа и просмотр его событий. На всех репликах следующий запрос учитывает отзыв, в том числе
  в браузерной сессии, открытой отозванным ключом. Сотруднику после входа открывай только его статистику запросов, замен
  и ошибок. Просмотр исходных фрагментов — отдельное полномочие. Изоляцию обеспечь для списка, счётчиков,
  детальной карточки и экспорта, включая запрос к URL напрямую. Поддержи существующие русский и английский
  интерфейсы.
• Перед доработкой UI используй установленный .agents/skills/modern-web-guidance/SKILL.md. Сделай реестры
  семантическими таблицами. Свяжи заголовки с ячейками через th и scope, сделай область прокрутки доступной
  с клавиатуры. Сохраняй фильтр и фокус, когда список обновляется. При неизвестном объёме работы покажи этап
  и прошедшее время. Для измеримого объёма используй подписанный progress, для токенов/с нужны реальные
  отсчёты. Завершение операции сообщай текстом без перехвата фокуса. Проверь сценарии администратора и
  сотрудника в Playwright через настоящий сервер.

Экран «Защита запроса» в переписке

• Добавь этот экран уже в core в карточку вопроса. Если вопрос породил несколько вызовов или повторов,
  дай выбрать конкретную попытку. На одном экране без переключения вкладок покажи два блока. «До отправки
  основной модели» перечисляет замены, блокировки и представление значения в исходящем запросе.
  «Найдено после ответа» показывает поздние находки и источник каждой — исходный запрос, ответ поставщика
  или результат инструмента. Рядом с каждым вхождением покажи, кто его обрабатывал и в каком виде.
  Сохрани переход к подсвеченному месту и действие «Создать правило для следующих запросов».
• В core проведи через экран реальную локальную проверку завершённого вопроса средствами Kaponir, когда
  политика разрешает обработку нужного фрагмента. Отличай «Не запускалась», «В работе», «Ошибка» и
  «Завершена, находок нет». По мере подключения фоновых и внешних анализаторов добавляй их в те же строки.
  Более позднее обнаружение в исходнике, отправленном открыто, и первое появление значения в ответе имеют
  разные последствия. Если оно уже ушло токеном, поздняя находка сохраняет отметку о той замене.
• Указывай конкретного обработчика (правило, RapidOCR, S1, модель проверки) и применимое имя подключения
  или модели. Для места обработки на момент вызова используй «Локально», «Сервис компании» или «Внешний сервис».
  Если контур не зафиксирован, напиши «Неизвестно». HTTP совместим и с внутренним развёртыванием.
  У основной модели и каждого анализатора свои получатель, попытка и объём данных. Покажи, были ли это
  признаки, токен, исходное значение, фрагмент либо изображение. Для S1 сверяй фактические поля L0/L1/L2,
  включая разрешённый профиль, если он отправлен. Признаки L0 тоже являются передачей данных.
• Привязывай наблюдения к организации, вопросу, конкретной попытке и вхождению с ролью источника.
  Фиксируй преобразование на границе окончательно собранного исходящего сообщения и состояние отправки.
  Блокировка до отправки, попытка с неизвестным исходом и полученный ответ поставщика различимы.
  Присутствие поздно найденной строки проверяй по сохранённому в рамках политики исходящему содержимому
  или достоверной записи именно об этом вхождении. Хеш сообщения, текущие правила или совпадение
  текста в сессии сами по себе этого не устанавливают. При недостатке данных показывай «Неизвестно».
  История сохраняет решение и контур того момента даже после принятия правила или изменения подключения.
• По умолчанию показывай тип, маску и метаданные. Фрагмент с оригиналом открывается по отдельному праву
  в пределах срока хранения, обращение попадает в аудит. Для этого экрана не создавай бессрочную копию
  переписки. Сотруднику с доступом только к своей статистике исходные фрагменты недоступны и через API.

Развёртывание этапа 1

• Дай оператору Helm chart (предлагаемый путь deploy/helm/kaponir/), пример values для Minikube и описание
  параметров. Отдельные Deployment для admin, HTTP-воркеров и analysis, один Service перед N ≥ 1 готовыми
  HTTP-репликами. Увеличение N не меняет адрес, ключ клиента или vault. Между запросами sticky sessions не
  требуются. Открытый SSE завершает принявший его под. Укажи исполняемую команду, версию образа и условия
  готовности для каждой роли. В следующих этапах добавляются пулы OCR. В values опирайся на workerPools и sessionCache из
  раздела «Как добавить воркер» корпоративной архитектуры. Админка не участвует в синхронном пути запросов.
• Уже в core сделай экран «Воркеры» для HTTP и analysis. Покажи desired/ready, UID, версию политики и причину
  Pending/NotReady. Для HTTP покажи активные запросы и SSE, сопоставь Deployment и EndpointSlice своего Service.
  Для analysis сверь UID с heartbeat исполнителя, покажи активное задание и время последнего обновления.
  В карточке пула обязательна кнопка «Изменить число воркеров». В ручном режиме
  оператор вводит итоговое число и нажимает «Применить». Через административный API и namespaced
  deployments/scale измени размер пула. Покажи готовность («Готовы 2 из 3»), запуск и завершение подов
  до фактического результата без ручного обновления. Ограничь операцию списком Deployment, полномочием
  оператора, пределами установки и защитой от конкурирующих изменений. Запиши автора и старое/новое
  значение в аудит. Пользователю админки достаточно браузера.
• PostgreSQL доступен по сети. Приложение поддерживает внешний PostgreSQL. Для стенда подходит отдельный
  StatefulSet с PVC для данных и WAL. У HTTP-воркеров нет общего каталога SQLite и нет требования к
  отдельному PVC для vault. Выдели отдельную роль БД для миграций и одну миграционную Job с блокировкой
  конкурентного запуска, безопасным повтором и проверкой версии схемы. Изменения схемы должны быть
  совместимы с rolling update. Для восстановления нужны БД и нужные версии ключей.
• Раздели startup, liveness и readiness. В готовности учитывай рабочий движок, PostgreSQL, доступный ключ и
  опубликованную политику. При пропаже БД сними готовность. В liveness проверяй жизнь самого процесса. При
  SIGTERM закрой приём новых запросов, дай активным потокам закончиться в пределах grace period, зафиксируй
  вынужденные обрывы. Задай requests/limits, ограниченные очереди, размеры тела, таймауты и пределы пула БД
  с учётом N. Включи минимальные ServiceAccount/RBAC, non-root, seccomp, отсутствие лишних capabilities,
  защищённый внутренний порт и NetworkPolicy для нужных соединений. Опиши TLS и доверие между ролями.
  Значения секретов не должны оказаться в Git, Helm values, диагностике или метках Prometheus.

Настройки установки и внешний PostgreSQL в этапе 1

• Сделай «Настройки» постоянным пунктом бокового меню для пользователей с соответствующими правами. Первая
  страница — «Настройки → База данных». Подключение общее для всей установки. Проверяй отдельное серверное
  полномочие при просмотре параметров, проверке и применении. С дашборда «Хранилище и поставщики» веди сюда
  ссылкой. Будущий раздел «Вход и SSO» показывай при поставке этой функции и в контексте выбранной организации.
• Поддержи установку с PostgreSQL рядом с приложением и с существующим PostgreSQL в другом кластере или
  управляемом сервисе. Во внешнем режиме chart не создаёт StatefulSet или PVC для БД. Для новой установки
  предложи «Подключить существующую базу», для действующей покажи состояние и «Изменить подключение».
  Оператор задаёт хост, порт (по умолчанию 5432), имя базы, пользователя и при необходимости корпоративный
  CA. Принимай пароль по HTTPS как поле
  только для записи или ссылку на разрешённый Secret. Учётные данные мигратора отдели от рабочих.
  Храни активную и проверяемую конфигурации вне целевой БД в заранее выделенных ресурсах namespace.
  Рабочим подам выдавай только их секрет. Учитывай сетевую политику установки. Используй сохранённый
  секрет только для разрешённого ему адреса. В UI и событиях показывай безопасные реквизиты и версию.
• Для новой установки без активной конфигурации дай доступ к этой же форме через одноразовый секрет
  установщика. Мастер доступен до миграций и подключения обычной авторизации. Сделай отдельную стадию
  bootstrap, чтобы Helm --wait мог завершиться с готовым мастером. После «Применить» выполни миграционную
  Job и допусти рабочие пулы без второго ручного запуска Helm. Вариант с заранее заданным Secret поддержи
  для автоматизированной установки. Состояние завершения bootstrap переживает рестарты и потерю связи с БД.
• «Проверить подключение» выполняет ограниченные по времени проверки DNS/TCP, TLS (verify-full с доверенным
  CA), входа, совместимости схемы и прав чтения/записи по каталогу привилегий. Проверь пути от admin, HTTP,
  analysis, установленных OCR-пулов и мигратора их собственными ролями и сетевыми политиками. Для ещё
  не запущенной роли подходит временная проверка с теми же условиями. Проверка не пишет данные. Покажи этап
  и результат, связывай ошибку с полем. Объявляй итог через role="status", сохраняй введённые несекретные
  значения. Изменение любого параметра или версии Secret требует повторной проверки перед применением.
• Переключение защищай версией активной конфигурации и одной операцией на установку. При смене пароля
  к той же базе открой новые пулы соединений и убедись в их готовности до закрытия старых. При смене самой
  БД покажи исходную и целевую базы. Для переноса обеспечь паузу и завершение всех источников записи,
  включая админку и фоновые задачи, затем сверь с целью финальную точку переноса, ID установки, схему
  и доступ к нужным версиям ключей vault. Один ID также есть у устаревшей копии. Пустая база подходит
  для нового развёртывания. Существующая установка принимает подготовленную актуальную копию. Перенос данных
  выполняется отдельной процедурой. Перед допуском трафика исключи запись старым поколением подов, проверь
  готовность всех ролей на одной версии. Ошибка проверки до применения сохраняет активное подключение.
  После первой записи в новой базе возврат требует сверки данных. В аудит запиши оператора, версию и исход.
  Для установки под GitOps направляй применение из UI через настроенный процесс и показывай статус синхронизации.

Дальше — границы следующих поставок

• Общий сессионный кеш опционален. Первый сквозной сценарий должен работать с одним PostgreSQL.
  Подключай Redis для индекса сессия → вопросы/вызовы и производных метаданных, если выигрыш подтверждён
  замером. Ключ включает организацию, видимость и версию, TTL ограничен retention. После фиксации изменения
  обнови версию. Задай тайм-аут, ограниченный переход к БД и защиту от одновременного прогрева. Не кешируй
  оригиналы, ключи, полномочия на раскрытие и решения об отзыве. Состояние общих бюджетов и очередей
  остаётся в БД. Базовый Redis работает без диска. Режим RDB/AOF с отдельным PVC поддержи для установок,
  где нужно сократить прогрев после рестарта самого Redis. Горячий кеш и доступность БД проверяй независимо.
• Контракт очередей. Реализуй его для analysis уже в этапе 1 и переиспользуй при подключении OCR.
  HTTP или admin API транзакционно создаёт задание в PostgreSQL.
  Пул kaponir-analysis читает analysis, kaponir-ocr-batch читает ocr.batch, kaponir-ocr-inline читает
  ocr.inline. Тип и очередь входят в фильтр захвата. Фоновое задание содержит стабильный ключ операции и
  ссылку на зашифрованный вход с TTL. В короткой транзакции используй FOR UPDATE SKIP LOCKED. Установи UID,
  lease_until и новый номер попытки, освободи соединение. Продлевай аренду. Успешная фиксация проверяет
  действующую аренду и номер попытки, атомарно сохраняет результат, вхождения и статус. После падения
  возможен повтор без дублей. Ограничь попытки и время, сохраняй причину и отложенный повтор. Уведомление
  PostgreSQL может ускорить опрос. Пропуск уведомления не теряет работу. Пока анализ ждёт дочерний OCR,
  его вычислительный слот свободен. Неподтверждённый внешний вызов допускает повтор по контракту провайдера.
• Один образ OCR, отдельные пулы для защиты перед отправкой и пакетного импорта. Для срочного пула зарезервируй
  ресурсы и минимум одну готовую реплику при включённой защите. HTTP ждёт проверенный результат ocr.inline
  в пределах общего дедлайна без открытой транзакции. Проверь привязку результата к запросу и текущей
  политике. При тайм-ауте, отмене или ошибке страницы возвращай явный результат, исключи отправку оригинала
  и любую отправку по позднему завершению. Сохрани поведение v1.0.3 для изображений и PDF, включая порядок
  страниц, лимиты параллельности и растра, удаление текстового слоя и вложений из подготовленной копии PDF.
• Скейлинг. Для HTTP используй HPA по CPU либо активным запросам при наличии адаптера. Для потребителей
  предусмотрен KEDA PostgreSQL scaler по агрегатному представлению готовой работы и активных аренд,
  с минимальным/максимальным размером, стабилизацией и отдельным пулом БД. Оператор также может выбрать
  ручной режим. Подключи оба пула OCR к экрану управления HTTP и analysis. Для автоматического режима
  дай оператору на экране менять минимум и максимум через объект владельца (HPA либо KEDA ScaledObject).
  Сохраняй нижнюю границу в одну реплику для HTTP и включённого OCR вложений. Если конфигурацией управляет
  GitOps, отправляй изменение из админки через настроенный процесс GitOps и показывай его синхронизацию.
  Один Deployment имеет одного владельца масштаба. При остановке HTTP снимает readiness
  и завершает SSE, потребитель прекращает захват и завершает активную аренду либо даёт ей истечь.
  Для пакетных работ реализуй авторизованные паузу захвата, возобновление и контролируемый повтор.
• Общий разбор. HTTP- и фоновые воркеры пишут находки в один журнал. Фоновое задание использует аренду с
  таймаутом и безопасный повтор после падения. Отдельно храни отправителя, владельца значения, команду/ключ
  при запросе, источник и позиции, фактический vault при запросе, будущий vault и область правила. Не
  угадывай автора импорта. Группировка выполняется только внутри доступного контура, фильтры сотрудника,
  команды, ключа и vault применяются к одному вхождению до подсчёта. В UI видны фрагмент, рекомендация ИИ,
  решение человека и круг получателей. Принять, исправить, отклонить или отложить ведёт к следующей карточке
  с теми же фильтрами. После принятия опубликуй версию политики, закрой уже покрытые находки, сохрани
  историю и аудит.
• Живой дашборд. Админка читает желаемое число реплик из Deployment, готовые адреса из всех EndpointSlice
  нужного Service, связывает их по UID пода. Данные внутреннего API каждой реплики обновляются примерно раз
  в 5 с, после трёх пропусков помечаются устаревшими. При переподключении UI получает снимок. Покажи
  активных уникальных сотрудников, запросы и SSE, шаг запроса, CPU/память и лимиты, размер и возраст
  очереди, задержки mask/restore, ожидание БД и первого токена поставщика. Устаревшая метрика не равна нулю.
  Клиентские ID доступны лишь через авторизованный admin API.
  Построй рабочие экраны «Обзор», «Воркеры», «Очереди и OCR», «Защита данных», «Клиенты и расходы»,
  «Хранилище и поставщики» по таблице редакции 9. Для потребителей сопоставляй поды с heartbeat из БД.
  Добавь переходы от пула к заданию, от запроса к получателю, от команды к попытке и расходу. На обзоре
  размести виджет «Что не успели скрыть». Считай уникальные пары «отправленная попытка + открытое вхождение»
  с доказанным открытым представлением у основной модели, отдельно — затронутые запросы и покрытие проверки.
  Неизвестные случаи, находки только в ответах, блокировки и передачи анализаторам показывай отдельно.
  Фильтрация по доступу предшествует агрегации. По клику открывай отфильтрованные карточки «Защита запроса».
• Совместимость. Добавь Anthropic Messages/count_tokens, инструменты и sidecar с теми же границами прав.
  Если /api/v1/deanonymize/stream получает фрагменты отдельными HTTP-запросами, обеспечь их порядок и
  доступность состояния при смене реплики, с ограничением размера и сроком жизни. Сохрани группировку ходов,
  служебных названий и субагентов без смешения пользователей. Для изображений сохрани RapidOCR, непрозрачную
  заливку всех чувствительных областей и остановку отправки при ошибке включённой защиты. Удалённый S1, OCR
  или мультимодальный анализ сырых данных требует разрешённого доверенного подключения.
• Датасет задаётся при установке через modules.dataset.enabled для всех ролей. Зафиксируй момент вступления
  нового значения в силу для всей установки. Защити запись от реплики со старой конфигурацией во время
  rolling update. При false старые и новые клиенты получают 404 на операции модуля, отсутствуют кнопки,
  статусы, флажок и клиентский сбор, старые задания больше не пишут примеры. Решения и аудит продолжают
  работать. Повторное включение возвращает доступ к ранее сохранённым данным в пределах retention. При true
  начальный автосбор выключен, выборка создаёт черновики, явное решение по одному однозначному фрагменту
  может создать проверенный пример.
• Управление затратами. Общий бюджет команды атомарно резервируется в PostgreSQL до вызова по верхней оценке
  входа и ограниченного ответа. Попытка имеет уникальный ID. Закрывай резерв по usage один раз, при
  неопределённом исходе оставь на сверке. Учитывай входные, выходные и кешированные токены, версию тарифа,
  валюту, фиксированную подписку и квоту. Повторный вызов, служебное название сессии и шаг инструмента имеют
  собственную атрибуцию. История расходов переживает перевод сотрудника. Для профиля orion/auto учитывай
  квоты, инструменты, контекст и зону данных. После выдачи первого фрагмента SSE автоматический повтор
  запрещён. До выдачи учитывай, мог ли уже выполниться инструмент с побочным эффектом. Явная модель
  сохраняется, если замена не разрешена политикой.
• Для командных пулов держи раздельные квоты подписок и API-аккаунтов. Включай только подключения, для
  которых разрешено общее использование. Профиль orion/agent с отдельным планировщиком и исполнителем
  допускается после сравнения с одной моделью по качеству, задержке и стоимости решённой задачи. Каждый шаг
  заново проверяет права, маскирование и бюджет. Свободный canvas маршрутов и словарей остаётся в ROADMAP.
  Его реализация не входит в начало пилота.
• Следующий этап портала — опциональный SSO по OpenID Connect. Используй поддерживаемую библиотеку OIDC,
  Authorization Code с PKCE S256, одноразовые state и nonce, точный redirect URI и проверку подписи по JWKS
  доверенного issuer, iss, aud и срока ID-токена. В «Настройки → Вход и SSO» уполномоченный администратор
  задаёт для своей организации issuer, client ID, ссылку на Secret и привязку (организация, iss, sub)
  к существующему ID сотрудника. Не связывай
  по одному email. Пусть оператор проверит вход перед включением обязательного SSO. Привязка и повторный
  вход сохраняют прежние vault, ключи и команду. На входе предложи «Войти через компанию». Ограничь права
  текущими назначениями Kaponir. При включении обязательного SSO закрой в этой организации обмен API-ключа
  на браузерную сессию и заверши уже выданные по ключу браузерные сессии. Проверяй способ входа также
  в API интерактивной админки. IDE и сервисы используют собственные ключи.
  Проверяй блокировку сотрудника на следующем обращении во всех ролях. Для отключения только у IdP задай
  конечный срок до повторной аутентификации, отдельно объясни оператору отзыв API-ключей. При недоступном IdP
  новый SSO-вход завершается явной ошибкой, шлюз продолжает обслуживать действующие ключи. В аудит пиши
  результат, организацию и ID, исключи токены, коды авторизации и секрет клиента.

Как сдавать

Прогони форматирование, Clippy, Rust/Python-тесты, затронутые браузерные проверки и регрессии Community из
.github/workflows/ci.yml. Для Enterprise добавь интеграционные тесты с настоящим PostgreSQL и тестовым
поставщиком. Докажи конкурентное выделение токена, разграничение пользователей и организаций, отзыв ключа на
другой реплике, отсутствие вызова поставщика при неудачной записи и восстановление после backup в отдельную
БД с нужными версиями ключей. Приложи карту входных маршрутов, схему миграций/ротации, точную команду
установки, имена values, SHA и результаты. Для HTTP и analysis приложи команды запуска из chart, imageID,
результат проверки общего ядра и сквозную связь «вопрос → задание → вхождение» после замены пода.
Для независимой приёмки core в Minikube опиши установку, выдачу
ключей через штатный интерфейс, подключение тестового поставщика, поиск pod UID в авторизованном журнале и
процедуру backup/restore. Отдельно укажи, что ещё предстоит для полного корпоративного пилота. Числа стенда
хранилища не используй как RPS шлюза.
Опиши установку с внешней БД через браузер с нуля, смену адреса и восстановление подключения при недоступной
активной БД через штатные полномочия оператора установки. Восстановление не должно повторно открывать мастер.

Когда корпоративную сборку можно установить, передай агенту приёмки заявленную версию приложения,
Git SHA, образ и chart. Для обновления укажи также предыдущую поддерживаемую сборку Enterprise и штатную
команду обновления. По этим данным агент сможет сверить kaponir --version внутри пода и повторить
проверку старой подстановки через публичный API после миграции и после восстановления из копии.
