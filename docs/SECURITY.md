# Безопасность и модель доверия

[Главная](../README.ru.md) · [Карта документации](README.md) ·
[Архитектура](DESIGN.md#8-модель-угроз-и-rbac) · [Эксплуатация](OPERATIONS.md)

Kaponir уменьшает раскрытие исходных значений внешнему LLM-провайдеру. Он не создаёт изолированную
среду, не заменяет управление секретами и не гарантирует обнаружение всех конфиденциальных данных.
Безопасность зависит от правил, детекторов, режима S1, ключей и защиты машины, где запущен процесс.

## Что защищает система

Основной сценарий: доверенный локальный процесс получает исходный текст, заменяет найденные значения
и передаёт обработанный запрос внешнему сервису. Соответствия токенов остаются в vault.

```text
Доверенная зона                         Менее доверенная зона
┌────────────────────────────┐          ┌──────────────────────┐
│ клиент → Kaponir → upstream├─────────→│ LLM / S1 HTTP        │
│          │                 │          │ получает обработанные│
│          └→ vault + ключи  │          │ данные по протоколу  │
└────────────────────────────┘          └──────────────────────┘
```

При использовании сохранённого подключения upstream получает ключ поставщика от Kaponir. При S1
L1/L2 внешний оценочный сервис дополнительно получает разрешённые значения и/или контекст.
Теневой режим не уменьшает это раскрытие: он только запрещает оценке менять решения.

## Что находится за пределами защиты

- Администратор или процесс, способный читать `KAPONIR_HOME`, память процесса или переменные окружения,
  может получить исходные данные и ключи.
- Вредоносный клиент с доступом к API может использовать возможности пространства в пределах его токена.
  Отдельной многопользовательской RBAC и индивидуальных клиентских ролей сейчас нет.
- Детектор может пропустить секрет. S1 оценивает только найденных кандидатов, OCR только извлекает текст.
- Сторонний upstream, сеть и клиент имеют собственные журналы и политику хранения; Kaponir ими не управляет.
- Модель может изменить или не вернуть токен. Восстановление не исправляет произвольный искажённый ответ.
- Контуры Personal/Team/Global управляют правилами и записями, но не являются полноценной границей
  между пользователями одного доверенного сервера.

## Локальное пространство и ключи

`KAPONIR_HOME` задаётся глобальным `--home`, одноимённой переменной окружения, затем используется
`$XDG_CONFIG_HOME/kaponir` или `~/.config/kaponir`. `init` создаёт каталог с правами `0700` на Unix
и ключевые файлы с ограниченными правами.

| Данные | Назначение | Последствия потери |
|---|---|---|
| `vault.key` / `KAPONIR_VAULT_KEY` | Мастер-ключ шифрования vault и защищённых настроек. | Старые соответствия, журнал, подборка и сохранённые ключи поставщиков невозможно расшифровать. |
| `token.key` / `KAPONIR_TOKEN_KEY` | HMAC-токены и суррогаты; необязательный общий ключ команды. | Детерминированные псевдонимы нового пространства могут измениться; HMAC-режим не восстанавливает оригинал. |
| `vault.db` | SQLite: соответствия, blind index, журнал, сессии и зашифрованные настройки. | Теряется обратимость и история, даже при сохранённом ключе. |
| `rules/*.toml` | Точные правила и политика контуров. | Теряются подтверждённые решения; сами файлы могут содержать закрытые значения открытым текстом. |
| `config.toml` | Настройки движка, S1, сервера и worker. | Теряется конфигурация; API-токен может находиться здесь, если не задан окружением. |

Значения vault шифруются ChaCha20-Poly1305. Слепой индекс позволяет искать каноническое значение
без хранения его открытым индексом, но не делает файл безопасным для публикации. Ключи поставщиков
также хранятся зашифрованными; API возвращает признак наличия ключа, а не его значение.

Переменные окружения удобны для служб и контейнеров, но доступны владельцу процесса и потенциально
системной диагностике. Не передавайте секреты в аргументах командной строки и не записывайте их в shell history.

## Токены и обратимость

- Обычные токены вида `ANON_<KIND>_<N>` требуют соответствующей записи vault и прав доступа principal.
- DNS-формы предназначены для hostname и pod-like контекстов.
- HMAC-псевдонимы стабильны для одного ключа, но не содержат обратимого соответствия.
- `mask --irreversible` не записывает новые соответствия; восстановление исходных значений невозможно.
- `mask --dry-run` откатывает сохранение. Не используйте его результат как рабочий обратимый запрос.
- Журнал спорных решений содержит исходные значения и имеет TTL; очистка выполняется `journal purge`.
- Сессионная память также содержит зашифрованные исходные значения и очищается по TTL журнала.

Токены — не шифротекст и не доказательство отсутствия утечки в остальном тексте. Перед отправкой
проверяйте результат, особенно при новом типе документа.

## Раскрытие через S1

| Режим | Что получает HTTP S1 |
|---|---|
| L0 | Типы, источник, числовые признаки и хеши триграмм; исходная строка и контекст — `null`. |
| L1 | L0 и само значение кандидата. |
| L2 | L1 и ограниченное окно контекста; другие найденные кандидаты заменяются метками. При наличии контекста может передаваться отдельный профиль точных MASK-правил. |

L0 не является анонимизацией самих признаков или хешей. На L2 нераспознанные секреты могут остаться
в контексте. Credentials ограничиваются L0, категория `credential` и `SECRET` исключаются из профиля;
новые SECRET-кандидаты discover не передаются на оценку. Эти ограничения не заменяют проверку
остального контекста.

Для внешнего S1 выбирайте доверенный endpoint и минимально необходимый уровень. Локальный `ngram`
использует L0 и не отправляет сетевых запросов. Подробности — [S1](S1.md#что-получает-провайдер).

## Сеть и доступ

- По умолчанию `serve` слушает `127.0.0.1:8787`; UI и REST используют тот же процесс.
- Нелокальный `listen` требуется защищать `[serve].api_token` или `KAPONIR_API_TOKEN`.
- Для REST используется `Authorization: Bearer`; для прокси — `x-kaponir-token`.
- Без API-токена действует проверка loopback-имени `Host` для защиты от DNS rebinding.
- Worker на нелокальном адресе требует собственный `KAPONIR_WORKER_TOKEN`; управление заданиями
  проверяет авторизацию, Content-Type и Origin.
- Для доступа между машинами используйте TLS reverse proxy или доверенную защищённую сеть. Сам HTTP
  listener не заменяет TLS, ограничение клиентов и политику firewall.

Один API-токен даёт широкий доступ к пространству. Не публикуйте UI, REST или worker напрямую в интернет.
Не помещайте токены в URL, журналы, примеры запросов или экспорт без необходимости.

## Документы и worker

Worker ограничивает ввод разрешённым `input_root`, не обходит symlink и не принимает выход за этот
каталог. Это граница области анализа, а не sandbox против администратора хоста. Исходные документы
не копируются в очередь; SQLite очереди содержит пути и техническое состояние, но не распознанный текст.

При локальном импорте извлечённый текст временно помещается в закрытый каталог и удаляется после
обработки. Кандидаты и короткие примеры затем хранятся в зашифрованном vault. При worker на другом
сервере исходные документы и OCR обрабатываются уже в его зоне доверия, а кандидаты передаются proxy API.

OCR-веса и runtime загружаются отдельно, SHA-256 фиксированных артефактов проверяется. Это проверка
целостности конкретной загрузки, не гарантия безопасности всей сторонней цепочки поставки.

## Резервное копирование и восстановление

Для обратимости старых токенов резервируйте **вместе**:

1. `vault.db`;
2. `vault.key` и `token.key`, если последний существует;
3. `config.toml` и `rules/`;
4. при необходимости `s1/`, `worker/`, внешние пакеты и модели.

Остановите процессы записи или используйте согласованный SQLite backup. Простое копирование базы во
время транзакции может дать несогласованный снимок. Храните резервную копию зашифрованной, ограничьте
доступ и отдельно проверьте тестовое восстановление в новом временном `--home`.

Никогда не помещайте backup, `vault.key`, `token.key`, ключи поставщиков или реальные документы
в репозиторий. Не удаляйте `vault.key` отдельно от намеренного удаления всего пространства.

## Экспорт настроек — не backup

`kaponir config export` переносит конфигурацию, правила и подключения, но не таблицы восстановления,
ключи vault/HMAC, журнал, сессии, подборку discover и обучающие метки. По умолчанию ключи подключений
не включаются. `--include-secrets` создаёт **незашифрованный** JSON с секретами.

Даже экспорт без ключей содержит точные пользовательские правила, адреса и имена подключений.
Обращайтесь с ним как с конфиденциальным файлом. Подробности — [SETTINGS_TRANSFER.md](SETTINGS_TRANSFER.md).
